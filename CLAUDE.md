# Pet Adopt: notes for Claude Code

Open-source storefront for adoptable pets. Visitors browse a catalog and contact the owners on WhatsApp or social media. No visitor accounts. Only the owners sign in, add pets, and build pages with a drag-and-drop editor.

Stack (versions pinned on purpose): Next.js 16.3.3, Drizzle ORM (SQLite via better-sqlite3, PostgreSQL via pg), Better Auth 1.7, Puck (`@puckeditor/core` ^0.24), shadcn/ui on Tailwind v4, React 19.2, TypeScript 5.7. **No Payload**: it was removed; the backend is our own (`src/db`, `src/server`).

## Layout (pnpm workspace + Turborepo)

- `apps/web`: the Next.js app, backend included (`src/`, `scripts/`, `drizzle/`, `pet-adopt.config.ts`, `.env`). Paths in this file that start with `src/`, `scripts/` or `drizzle/` are inside `apps/web`. Its scripts run with `apps/web` as the working directory.
- `packages/plugin-sdk` (`@pet-adopt/plugin-sdk`): what plugins and `pet-adopt.config.ts` import (`definePlugin`, `defineConfig`, `Plugin`, `EmailSender`, `PluginUser`...). It imports nothing from the app; keep it that way, so an npm plugin depends on it alone.
- `plugins/*`: workspace plugins (`@pet-adopt/plugin-adoption-tips`, `-resend-email`, `-form-builder`), each depending only on the SDK. The app lists them in `next.config.ts` `transpilePackages` (they ship TypeScript source, no build step); add a new one there and to `apps/web/package.json`.
- The registry, icon checks and plugin runtime stay in the app (`apps/web/src/plugins/`).
- `data/` (git-ignored, repo root): local SQLite file and uploads. Defaults `DATABASE_URL=file:../../data/pet-adopt.db` (`DEFAULT_SQLITE_URL` in `client.ts`) and `UPLOAD_DIR=../../data/media`, relative to `apps/web`. SQLite creates the folder on open, never during `next build` (a missing folder counts as "no database" for the build fallback).
- Root scripts go through turbo (`pnpm typecheck`, `lint`, `build`, `check:schemas`, `check:backend`, `dev`) or `pnpm --filter @pet-adopt/web` (`migrate`, `seed`, `db:generate`, `admin:reset-password`). `turbo.json` uses `envMode: loose` so `DATABASE_URL` and friends reach the tasks. `turbopack.root` in `next.config.ts` is the repo root (pnpm installs `next` there and the plugins live outside the app).
- Drizzle stays in the app on purpose (one consumer); make `packages/db` only when a second program needs the database.

## Architecture

- **Routes:** `src/app/(frontend)` public site (`/`, `/pets`, `/pets/[slug]`, `/[slug]`). `src/app/(editor)/edit/[id]` the Puck editor (signed-in only). `src/app/media/[...path]` serves uploads. `src/app/api/auth/[...all]` is Better Auth. `/health` is a liveness probe. `src/instrumentation.ts` creates the first owner on start.
- **Database (`src/db`):** `schema/sqlite.ts` and `schema/pg.ts` are twins (Drizzle's two dialects have different table types). `client.ts` picks the dialect from `DATABASE_URL` (`postgres://` or else SQLite `file:`), enables SQLite foreign keys and WAL, and provides `withTransaction`. SQLite applies pending migrations on first open; Postgres needs `pnpm migrate`. `pnpm db:generate` writes `drizzle/sqlite` and `drizzle/pg`; `pnpm check:schemas` fails when the schemas drift.
- **One set of repositories:** `src/server/*.ts` is written once against the SQLite-typed objects and cast to Postgres at one boundary in `client.ts`. Keep columns portable: ids are integers, timestamps are `Date`, booleans are booleans, lists and settings are JSON columns, date-only values are `YYYY-MM-DD` text, select options are plain text validated in the app. Case-insensitive search uses `lower(col) like`, not `ilike`. Run `pnpm check:backend` on both databases after data-layer changes.
- **Data layer (`src/server`):** `pets.ts`, `pages.ts`, `media.ts`, `settings.ts`, `users.ts` hold the rules that used to be Payload hooks. `result.ts` has `Fields` (collects one error per field, keys like `nav.0.href`), `ValidationError`, `UserError` and `run()`. `actions/*.ts` are the `'use server'` functions the UI calls: each does `requireUser()` or `requireAdmin()` and returns `ActionResult`. The public pages read through `src/lib/queries.ts`, which keeps the old names and adds the build-time fallback.
- **Auth (`src/server/auth.ts`):** Better Auth with the Drizzle adapter (`usePlural`), the admin plugin (roles `admin` and `editor`), email and password, no sign-up, 2 hour sessions, cookie prefix `pet-adopt`. Sign-in is throttled by `src/server/throttle.ts`, shared by `signInAction` and the HTTP route `/api/auth/sign-in/email`: each attempt is counted **before** the password is checked, in one atomic upsert on the `rate_limits` table in three limits: 30 per client address, 5 per email **per client** (the everyday lockout, so one machine cannot lock an owner out), and 100 per hour per email overall (caps guessing spread over many addresses). A lock does not extend while active (the timestamp freezes once the limit is hit), and emails are SHA-256 hashed in the keys so the table never holds attacker-sized strings. Parallel guesses cannot slip past, and rows are purged opportunistically. `changePasswordAction` and the HTTP route `/api/auth/change-password` share one per-user counter (`guardPasswordChange`, key `chpw:<userId>`); Better Auth's own address-keyed rules for `/sign-in/email` and `/change-password` are switched off in `auth.ts`. IPv6 clients are reduced to their /64 prefix (`ipv6Prefix64`; IPv4-mapped addresses count as the IPv4). Recovery for a locked-out owner is `pnpm admin:reset-password` (`scripts/reset-password.ts`, password from `NEW_PASSWORD`). Better Auth's own limiter is switched off for that path (it keys on one address and would share a single bucket across all owners when it cannot parse the proxy header) and server actions skip it anyway. The client address is the entry `TRUSTED_PROXY_HOPS` (default 1) from the end of `CLIENT_IP_HEADER` (default `x-forwarded-for`) and must be a valid IP; entries before it are client-controlled, so the site must run behind a proxy you control. With no usable address the per-client limit is skipped (no shared "unknown" bucket) and production logs a warning once. The route handler is an **allowlist**: only `/api/auth/sign-in/email`, `change-password`, `sign-out` and `get-session` are open; everything else Better Auth ships (update-user, admin/*, sessions, sign-up, password reset...) returns 404, so role changes go through `users.ts` (last admin cannot be demoted or deleted; the first account is always admin) and nothing a future upgrade adds is exposed by default. The server start (`instrumentation.ts`) throws in production for a weak `BETTER_AUTH_SECRET` or a missing `NEXT_PUBLIC_SERVER_URL`. Accounts are created with `$context.internalAdapter`.
- **Password reset** (`src/server/password-reset.ts`, actions in `actions/password-reset.ts`, page `/admin/reset-password`): one-time links `<NEXT_PUBLIC_SERVER_URL>/admin/reset-password?token=<32 random bytes, base64url>`, never built from the request's Host. Only `sha256(token)` is stored, in Better Auth's `verifications` table (identifier `pwreset:<hash>`, value = user id, no migration needed); valid 1 hour, one use (claimed by `DELETE ... RETURNING`, so parallel uses cannot both win), a new link cancels older ones, banned accounts get none. Using one writes the credential and deletes every session in one transaction, then lifts sign-in lockouts. Links come from an admin (`createResetLinkAction`) or by email (`requestPasswordResetAction`), which validates and throttles first (`guardResetRequest`: 10 per client per 15 min, 3 per email per hour, keys `pwreset:*`), then does the lookup and sending in `after()`, so the answer and its timing are the same for unknown addresses. The page sets `referrer: no-referrer`. Better Auth's own reset endpoints stay 404.
- **Email** is a plugin hook: a plugin may provide `email: { send(message) }` (`EmailSender` in `@pet-adopt/plugin-sdk`); `registry.ts` allows at most one and `getEmailSender()` returns it or null (no email form then). `plugins/resend-email` calls Resend's HTTP API with `fetch` (no package), reading `RESEND_API_KEY` and `EMAIL_FROM` at send time; `pet-adopt.config.ts` always registers it. An `EmailSender` may report `status()` (`EmailStatus`: provider, `ready`, non-secret `details`, `setup` text); `getEmailSender()` returns null while it is not ready, so nothing offers email the site cannot send, and `getEmailPlugin()` returns it either way for its admin page, which shows the status and a "Send a test email" form (`sendTestEmailAction` in `actions/email.ts`: admins only, 5 per 15 minutes per admin, key `emailtest:<userId>`). An SMTP or other provider is another plugin with the same shape.
- **Uploads:** `uploads.ts` checks the file really is JPEG/PNG/WebP/GIF with sharp (no SVG; **AVIF and HEIC are refused** with a message asking for JPEG, PNG or WebP, because their metadata, extra images and thumbnails are items in the file's offset tables that cannot be cut out and sharp does not report them all; sharp reports both formats as `heif`), refuses more than 40 megapixels, 12000 px on a side or 100 frames, then removes the metadata **without re-encoding** (`strip-metadata.ts`): it walks the JPEG segments / PNG and WebP chunks / GIF blocks and copies the ones that show the picture byte for byte, dropping EXIF (GPS, device, embedded thumbnail), XMP, IPTC, comments and anything after the end marker, so pixels, colour profile and animation are untouched (the check script proves identical decoded pixels). Orientation survives as a 26-byte EXIF block holding only that tag, so phone photos stay upright. Every format uses an **allowlist**: PNG and WebP copy only listed chunks, GIF only the image data plus timing and loop blocks that are **rebuilt from their fixed fields** (so extra bytes cannot ride along), and JPEG copies only the picture markers (tables, frame header, scan), the Adobe tag and the ICC profile, rebuilds the JFIF header with no thumbnail (JFIF can embed the original image), drops application segments and comments, and **refuses the whole file** on any other marker. The stripper fails closed: after it runs, sharp must read back the same format, size and frame count, or the upload is refused and the original is never stored. It names the result `<random hex>.<ext>` (the name people choose is only a label: `media.name`, migration 0009, cleaned by `cleanMediaName` in `src/lib/media-name.ts`, set from the upload dialog's "File name" or the uploaded file's own name, searched with the alt text), writes a `.thumb.webp` preview, and on any failure removes what it wrote and logs a file it cannot remove. Any decode failure becomes a field error on `file`. `storage.ts` is local disk (`UPLOAD_DIR`, default `data/media` at the repo root) or S3 when `S3_BUCKET` is set. URLs are `/media/<file>`; `next.config.ts` allows that path for `next/image`. Deleting an image that a pet, page or the logo uses is refused.
- **Pages:** `pages` has `puck_draft` and `puck_published` JSON columns, so saving a draft never changes the live page, and publishing copies draft to published (in one `UPDATE ... SET puck_published = puck_draft` when no data is sent, so a draft saved at the same moment cannot be overwritten). No version history, but `saveDraft`/`publishPage` take an optional `baseVersion` (the page's `updatedAt` in ms, returned as `version` by every save): if the page changed since, the save is refused with a "changed somewhere else, reload" error. The editor (`PageEditor`) carries it. Versions are matched as a one-millisecond window (`atVersion`), not with `=`, because PostgreSQL fills new rows with microsecond timestamps; each new version is `max(now, base + 1)`. `isPuckData` requires every block to have an object `props` and caps a layout at 1 MB and depth 30; NULs are stripped before saving. The slug `home` is the homepage (`HOME_SLUG`); reserved slugs are in `RESERVED_SLUGS`. `ensureHomePage()` (server start, `pnpm seed`, and `listPagesAction`) creates it when missing: title "Home", published, `DEFAULT_HOME_DATA` as draft, live and version 1. **System pages** (`SYSTEM_PAGES` in `src/server/pages.ts`, `SYSTEM_PAGE_SLUGS` / `isSystemPageSlug` in `src/puck/data.ts`): the homepage (`home`, id 1, `DEFAULT_HOME_DATA`) and the **Pets page** (`pets`, id 2, `DEFAULT_PETS_DATA` = one Pet catalogue block), ensured in that order by `ensureSystemPages()` (start, seed, pages list). Both keep their slug (a system page may save its own reserved slug, nobody else may take it), cannot be archived or deleted, and when unpublished their route shows the built-in layout. `/pets` renders the `pets` page through `BuilderContent` with the query string (`searchParams` in Puck metadata); the **Pet catalogue** block reads it via `metadata.fetchCatalog` (`queryCatalog` in `queries.ts`, which parses and checks the filters), shows a GET filter form to /pets, the grid and paging (`src/components/site/PetCatalog.tsx`); its resolved `catalog` prop is transient. The homepage is always **id 1** (`HOME_ID`): it is created there, and a homepage found under another id swaps ids with the page on id 1 (through a spare id; `page_versions.page_id` is `ON UPDATE CASCADE`, migration 0005, so histories follow), then the id counter is moved past the highest id (`setval` on Postgres, `sqlite_sequence` on SQLite). The homepage keeps its slug (a field error on `slug`) and cannot be archived or deleted (server and UI); it can be unpublished, and then `/` shows `DEFAULT_HOME_DATA`. `stripTransient` removes render-only props (PetGrid's `pets`); add any new resolved prop to `TRANSIENT_PROPS`. **Archive and versions:** `pages.archived_at` marks an archived page: off the site (`getPublishedPage` returns null), read-only (`saveDraft`, `publishPage`, `savePageDetails`, `restorePageVersion` refuse with "archived"), keeping its slug; `restorePage` brings it back as it was, and `deletePage` only deletes an archived page. Every draft save, publish and version restore writes a snapshot to `page_versions` (`number` per page, `kind` draft/published/restored, `created_by`) inside the same transaction, under the lock `pages:<id>`; a draft identical to the latest snapshot (compared with es-toolkit `isEqual`, because jsonb reorders keys) is skipped, and only the latest `KEEP_VERSIONS` (50) are kept. Restoring a version only replaces the draft. Snapshots do not count as image uses, so an image deleted later shows as missing in an old version. Signed-in previews: `/edit/<id>/preview[?version=N]` (editor layout, so the site CSS applies), shown in the admin table in a sandboxed iframe, which is why the CSP has `frame-src 'self'`.
- **Puck blocks:** all in `src/puck/config.tsx` (Hero, Text, Image + text, Features with icons, Call to action; Image grid (type `ImageGallery`), Image carousel, Video; Pet spotlight, Pet grid, Adoption steps, Numbers; Adopter stories, Team, Ways to help, Cost table, FAQ, Contact & map, Social links; Spacer, Divider). **Headings:** never write raw `<h1>`–`<h4>` in a block. Use `HeroTitle`, `Title` (block heading) and `ItemTitle` (one level below) in `config.tsx`, and `PetProfile`'s `level`. The tag comes from the render-only `headingLevel` that `assignHeadingLevels` (`src/puck/data.ts`, called by `BuilderContent` after data is resolved) sets: the first block that shows a heading gets 1 (the page's only `<h1>`), the rest 2; a page with no heading gets a visually hidden `<h1>` with its title. The size comes from the role class in `styles.css` (`.hero-title`, `.block-heading`, `.item-heading`, `.minor-heading`), never the tag, so promotion changes structure, not looks, and the editor (where `headingLevel` is unset) matches the live page. `PetCard` takes `headingLevel` (`h2` in the catalogue). Block options are optional props whose missing value means the original look, so older saved pages never change: `headingStyle` ('normal' | 'display', `headingClass`) on Hero, Image + text, Features, Pet spotlight, Pet grid, Cost table; `buttonStyle` / `buttonWidth` (`buttonClass`: solid, outline, dark; fit or full); Image + text also has `subheading`, `imageWidth` (half/wide), `photoMode: 'pair'` with `secondImage` and photo labels (real `figcaption` text on a dark chip); Hero has `layout: 'stacked'`; Features has `layout: 'list'` (heading beside stacked points). Pet spotlight `layout: 'profile'` and Pet grid `display: 'profiles'` render `PetProfile` from `PetSpotlightData` (labels, health checks, temperament, good with, rich-text description and health notes); the grid's resolved `profiles` prop is transient, and profile section headings sit one level below the pet name. The Cost table is a real `<table>` (caption, `th scope`) in `.table-scroll`; row highlights use theme pairs (`--warn-bg/--warn-ink`, `--primary/--on-primary`). `styles.css` defines `.sr-only` because the editor has no Tailwind. **Pet spotlight** stores only `petId` (picked with `PetPicker`, fed by `listPetChoicesAction` in `src/puck/actions.ts`) and resolves the pet at render through `metadata.fetchPet` (`getPetSpotlight`: null for unlisted, adopted or missing pets, which hides the block on the site); its resolved `spotlight` prop is in `TRANSIENT_PROPS`. **Block icons** come from `src/puck/icons.tsx`: a curated set of Feather icons converted once to plain SVG data with `toNavIcon` (react-icons cannot render in server components) and drawn by `BlockIcon`; add icons there, never render a react-icons component inside a block. Ways to help's payment details have a client `CopyButton`. The Video block embeds only what `safeVideoEmbed` (`src/lib/links.ts`) builds from a YouTube or Vimeo id (`youtube-nocookie.com`, `player.vimeo.com`, both in the CSP `frame-src`). The Image carousel is a client component (`src/components/site/ImageCarousel.tsx`, shadcn Carousel on Embla) styled by `.carousel-block` rules in `styles.css` keyed to shadcn's `data-slot` attributes, because the editor does not load Tailwind; do the same for any shadcn part used inside a block. The same components render on the server for visitors (`Render` and `resolveAllData` from `@puckeditor/core/rsc`, see `BuilderContent.tsx`) and inside the editor, so blocks stay free of hooks and browser-only code. They read site settings and pets through Puck's `metadata` (`PuckSiteMetadata`). The editor runs with `iframe: { enabled: false }` so the real site CSS applies; media queries don't emulate mobile. The editor's own UI follows the owner's light/dark mode like the admin (pre-paint script + `data-follow-mode` on `<html>` in the editor layout; `editor.css` overrides Puck's `--puck-color-*` variables, which Puck defines in `@layer puck-tokens`). The canvas is wrapped by `overrides.preview` in `.editor-canvas` and keeps the site's light colours unless the header's "Dark preview" switch is on (`forcedModeCss(theme, 'dark', '.editor-canvas[data-mode="dark"]')`). The admin pages table previews with `?mode=dark` the same way.
- **Pet form** (`(admin)/admin/pets/PetForm.tsx`, parts in `components/admin/pets/form/`): React Hook Form + zod (`src/lib/zod-schema/pet.ts`, which reuses the server's pure validators so the two cannot drift; the server stays the authority) + shadcn. Form values are plain strings, booleans and `{ id, thumbnailUrl, alt }` image refs with no zod transforms; `toPetInput` in `src/lib/admin/pet-form.ts` builds the `savePetAction` payload (blank text -> null; age fields only for the chosen `ageMode`, and **not at all for `keep`**, because resending `ageValue` re-estimates from today). Tabs: Basics, Health and behaviour, Photos and story, Adoption, Search and sharing; the sidebar holds status, flags and slug. WCAG 2.2 AA choices to keep: every control has a visible label, a "(required)" text mark, and its hint and error tied with `aria-describedby`/`aria-invalid` (`form/fields.tsx`; ids are `pet-<field>`); a failed save opens an `ErrorSummary` that takes focus, and its links switch to the field's tab (`FIELD_TAB`) and focus it; tabs announce their error count; photos are reordered with buttons, not only drag (`PhotosField`), with a polite live region; the media picker is a real dialog whose images are checkboxes, and its inner upload `<form>` calls `stopPropagation` because portal events still bubble to the pet form; the save button uses `aria-disabled`, not `disabled`, so focus is not lost; there is no sticky footer (it could cover a focused field). Server `fieldErrors` keys map onto form fields in `formFieldFor` (`photoIds` -> `photos`, `seoImageId` -> `seoImage`).
- **Plugins** (`pet-adopt.config.ts`, `src/plugins/` for the runtime, `packages/plugin-sdk` and `plugins/*` for the packages): `defineConfig({ plugins: [...] })`; `definePlugin` builds one (optionally with options). A plugin adds `screens` (served by the catch-all route `/admin/plugins/[plugin]/[[...path]]`, listed in the sidebar's "Plugins" group) and `dashboardWidgets`. `registry.ts` validates names, paths and widget ids at load and fails loudly. **Every plugin has a page:** a plugin may set `title` and `description`; one without a home screen (`path: ''`) gets the built-in `PluginOverview` at `/admin/plugins/<name>` (admins only: description, what it adds, and the email setup for the email plugin) and a menu entry, and `/admin/plugins` lists them all (`getPluginInfos`). A screen's menu look is `nav: { label, Icon }`. `Icon` is limited to a react-icons icon or `{ viewBox?, paths: string[], outline? }` (path data only, no markup); `src/plugins/icon.ts` checks it and turns it into plain SVG data (react-icons cannot render on the server, and a function cannot cross to the client nav), which `AdminNav` redraws. Anything else, or a tag or attribute outside the allowlist, throws when the config loads.
- **Caching:** public pages use `revalidate = 60` plus on-demand `revalidatePath` from the data layer (`safeRevalidate` swallows errors outside a request, e.g. in the seed script). `generateStaticParams` returns `[]`, so pages render on first visit.
- **Build without a DB:** `safely()` in `src/lib/queries.ts` returns fallbacks only while `NEXT_PHASE` is the production build, and SQLite opens with `fileMustExist` then, so `next build` never creates a database file. Anything that opens the database for a signed-in page must read `headers()` first (as `getSessionUser` does), otherwise Next prerenders the page at build time and a missing SQLite file fails the build with `SQLITE_CANTOPEN`.

## Behaviour worth knowing (carried over, still true)

- **Pet slug:** generated from the name when blank (numbered when taken, `pet-<time>` for names with no Latin letters), kept on partial updates, validated against `SLUG_PATTERN`. Not required in the form because it is filled on the server.
- **Species is free text, not an enum** (owners can add their own). `SPECIES` in `src/lib/options.ts` only holds the usual ones (curated labels, form suggestions). Values are stored normalised by `normalizeSpecies` ("Guinea  Pig" -> `guinea-pig`; blank keeps the current value, no letters or digits is a field error), and `conditions()` normalises the filter, so every caller matches. `getSpeciesOptions()` (visible pets only, or `includeUnlisted` for the admin) feeds the catalog dropdown: built-ins first, then custom ones. `labelFor` shows an unknown value humanised ("Guinea pig"). `status` is different: it is the `PetStatus` enum.
- **Age is worked out from the birth date** (`src/lib/age.ts`), so it keeps up with the calendar. `birthDate` (`YYYY-MM-DD`) is the one source of truth; `birth_date_estimated` marks one that came from "about 8 months" (`ageValue` + `ageUnit` in `savePet`, stored as today minus that, so it never drifts; saving the same date again keeps the flag; a blank date next to an age means use the age). `toPet` and `summaries` replace `ageDescription` and `ageGroup` with the live values ("About 8 months", `baby`) whenever a birth date exists, so every page that reads them updates with no change. Without a birth date the typed `ageDescription` and picked `ageGroup` are used. The catalog's age filter is a date range from one table of limits (`GROUP_LIMITS`: baby under 6 months, young under 2 years, adult under 8, then senior), shared by the label and the SQL, with the stored group for pets that have no birth date. Every age function takes `today` so tests can move time.
- **Admin pet list (`/admin/pets`) uses SWR, not server refreshes.** The filters are URL params parsed with nuqs (`search-params.ts`); `FilterBar` writes them (search debounced 300 ms, default `shallow`, so the server is not asked), `PetList` and `FilterBar`'s pager (`PetPagination`, shadcn's `pagination`, real `<a>` links built with nuqs's `createSerializer`, page window from `src/lib/pagination.ts`) both call `usePetList` (`src/lib/admin/use-pet-list.ts`), which reads the committed URL with `useSearchParams()` and fetches `listPetsAction` through SWR (one request for both; key `["pets", search, status, species, page]`; no `keepPreviousData`, so a filter combination that is not cached yet shows `PetListSkeleton`, 12 placeholder cards with deterministic, varied text widths). The server page only seeds the first render (`fallbackData`, for that key only). SWR's cache is an in-memory `Map` in `(admin)/providers.tsx`, keyed by user id, never persisted; The species dropdown in `FilterBar` is SWR too (key `["pets", "species"]`, seeded by the page's `speciesOptions` prop), so one `useInvalidatePets()` refreshes lists and species together; it (`src/lib/admin/pets-cache.ts`) must be called after anything that changes pets from the client, because `revalidatePath` does not reach the browser cache. Fetchers use `unwrapResult` (`unwrap-client.ts`) so `{ ok: false }` becomes a thrown error SWR can see.
- **Health notes are rich text** stored as a Tiptap/ProseMirror JSON document in `pets.health_notes_doc` (the old plain `health_notes` column is legacy: never written now, and an old value is read as a document by `toPet`). `src/lib/rich-text.ts` is pure and the one authority: `validateRichText` **rebuilds** the document from allowed parts only (paragraphs, bullet and numbered lists, bold, italic, underline, links), so unknown nodes, marks and attributes cannot get through; links must be `/path` or `http(s)://` with no credentials (`isAllowedHref`); 2000 visible characters. `Fields.richText` uses it in `savePet`, and the zod schema reuses it. The editor (`RichTextField.tsx`) imports individual Tiptap extensions, not the StarterKit, and `check:backend` asserts that list matches the validator. Public pages render it with `RichText` (`src/components/site/RichText.tsx`), as React elements, never HTML. The health notes are not shown on the pet page yet.
- **City and state** are normalised (trimmed, whitespace collapsed). Saving either rebuilds `location` as "City, State" (once if equal, case-insensitively); a pet with neither keeps its own `location`. Catalog filters on city and state match exactly; `getLocationOptions()` returns the distinct values of listed pets.
- **Unlisted pets:** `unlisted` is link-only. Every listing query goes through `conditions()` in `src/server/pets.ts`, which hides them unless `includeUnlisted` is set (only the admin action sets it, and `queries.ts` strips it for public callers). `getPetBySlug` ignores the flag and the page sets `robots: noindex`. Any new public listing must apply the same filter.
- **Description** is rich text, exactly like the health notes but capped at 5000 visible characters (`DESCRIPTION_MAX_CHARS`): JSON in `pets.description_doc`, the old `description` text column is legacy (read as a document, cleared on the next save). `savePet` still accepts a plain string (one paragraph per line). The public pet page draws it with `src/components/site/RichText.tsx`, which renders the allowed nodes as React elements (never HTML) and re-checks each link.
- **Links and embeds:** use `safeHref` and `safeMapEmbed` from `src/lib/links.ts` for anything an owner can type into a block; social URLs and menu links are validated on save. WhatsApp numbers go through `normalizePhone` (`(0)` trunk prefixes are dropped).
- **Site settings form** (`/admin/settings`, `SettingsForm.tsx`, schema `src/lib/zod-schema/settings.ts` reusing `validatePhone`, `validateWebUrl`, `validateLink`): tabs Brand (name, tagline, logo, site icon, light/dark switch), Contact (WhatsApp, message, address, hours, social links) and Navigation (menu links, footer); lists use `useFieldArray` with up/down/remove buttons announced in a live region; `settingsFieldInfo` maps dotted error keys (`nav.1.href`) to their tab and label. Theme fields are not in this form. **WhatsApp number** uses `PhoneInput` (`src/components/admin/PhoneInput.tsx`: a Combobox of countries searchable by name, ISO code or `+60`, plus the number; a number pasted with `+code` switches the country on blur, a valid one is regrouped) over `src/lib/phone.ts`, which wraps `libphonenumber-js/max` (Google's metadata in a smaller library; the `/max` build validates like Google's, the default build only checks lengths) for the country list, `validatePhone` (too short / too long / `not valid for <country>`) and `toE164`. The form schema and `updateSettings` both use `validatePhone`, and the server stores **E.164** (`+60123456789`); numbers without a code are read as `NEXT_PUBLIC_DEFAULT_COUNTRY_CODE` (default 60, Malaysia). The pet form's `contactWhatsApp` still uses the older `normalizePhone` check. **Logo and site icon** are two separate images: `logo_id` (any shape; site header and the admin sidebar in `AdminShell`, which also puts the site name in admin tab titles) and `favicon_id` (migration 0008; the SQLite file had `ON DELETE SET NULL` added by hand again). `faviconProblem` in `settings.ts` requires a square (within 5%) of at least 32 px. `siteIcons(settings)` in `queries.ts` turns it into `icons` metadata, used by all four root layouts (frontend, admin, auth, editor); none set means no icon tag. `mediaUsage` counts both, so neither can be deleted while in use. `getSettings` in `queries.ts` is wrapped in React `cache`, so layouts and pages share one read per request.
- **Theme library** (`/admin/theme`, admin only; `src/server/themes.ts`, actions in `actions/themes.ts`, UI in `src/components/admin/theme/`): owners' saved themes in the `themes` table (`name`, `base` preset, `settings` = the customTheme shape), one active via `site_settings.active_theme_id` (`ON DELETE SET NULL`; the SQLite migration 0007 had that clause added by hand because drizzle-kit dropped it). `getSettings()` lays the active theme over `theme` / `customize` / `customTheme` (and clears `primaryColor`), so every reader of the theme follows it with no changes. Saving uses the settings' `parseCustomTheme` and `contrastProblem`; the theme in use cannot be deleted; `activateTheme({ preset })` returns to a built-in preset as designed. The editor's live preview is `/edit/theme-preview` (real blocks): the editor posts `themeCss(...)` to it with `postMessage` and `ThemePreviewBridge` applies it (same origin only, CSS as text).
- **Theming** (`src/lib/theme.ts`, Theme tab of site settings): pure TS. `PRESETS` give light and dark base colours plus fonts, radius, button style, shadow, density and text size; `resolveTheme` sanitises every input and `themeCss` emits `html:root{...}` plus dark-mode rules. `ThemeStyle` injects it with `dangerouslySetInnerHTML`, safe only because of that sanitising, plus a constant pre-paint script for the saved light/dark mode (`pet-adopt-mode` in localStorage, `data-mode` on `<html>`). Custom colours are checked for 4.5:1 contrast on save (`contrastProblem`), reported as `customTheme.light.text`. Derived `--muted` and `--primary-text` are nudged (`ensureContrastOnAll`) to 4.5:1 on every background they appear on (`--bg`, `--surface`, `--surface-alt`, `--tint`), not just the page. Focus rings use full-opacity `ring-ring` / `outline-ring` (`--primary-text`, so at least 3:1); do not reintroduce shadcn's `ring-ring/50` when adding components. Every colour, radius, shadow, font and spacing value in `styles.css` is a variable: keep it that way. The page builder layout uses `lightOnly`. Fonts are self-hosted `@fontsource-variable/*` imports in `fonts.ts`.
- **shadcn/ui is site-wide.** `src/app/globals.css` (Tailwind, `tw-animate-css`, shadcn tokens) is imported by the frontend layout before `styles.css`. `@theme inline` there points shadcn's colour tokens at the site's own variables (`bg-primary` reads `--primary`, `text-muted-foreground` reads `--muted`, `bg-muted` reads `--surface-alt`), so components follow the theme and light/dark mode. The site's `--muted` is a text colour while shadcn's is a background: that is why they map differently. `styles.css` is unlayered, so it beats Tailwind's layered preflight and the public pages look as before. The editor layout does not load Tailwind. `src/components/ui/` is generated by shadcn. The shadcn style is `base-nova` (components are built on **Base UI**, `@base-ui/react`, not Radix; `radix-ui` was removed). Base UI has no `asChild`: to render something else use the `render` prop (`<Dialog.Trigger render={<MyThing />} />`). For a **link that should look like a button**, do not use `<Button render={<Link />} nativeButton={false}>`, which gives the link button semantics (role, Space activates it); style a plain `<Link>` with `buttonVariants()` instead (see `src/components/auth/AuthNav.tsx`). New components: `pnpm dlx shadcn@latest add <name>` generates Base UI versions; `src/lib/utils.ts` re-exports `cn` from the `cn` package, which shadcn's own init installed.
- **CSP** (`next.config.ts`): sent on every route. `default-src 'self'`; scripts and styles allow `'unsafe-inline'` (Next's inline bootstrap, and a nonce would end `revalidate` caching), plus `'unsafe-eval'` and `ws:` in development; `img-src 'self' data: blob:`; `frame-src https://www.google.com/maps/` (Contact block); `upgrade-insecure-requests` only when `NEXT_PUBLIC_SERVER_URL` is https. `CSP_REPORT_ONLY=1` switches to report-only. It is read at startup, so restart `next dev` after changing it. New external resources need a directive. The `/media` route's own stricter CSP is overridden by this global header.
- **Seed** (`scripts/seed.ts`): each step checks before it writes, so it is safe to re-run; it adds no pets if any non-sample pet exists, only fills settings while they are still the defaults, and refuses to run in production without `SEED_FORCE=1`. The owner comes from `SEED_ADMIN_*` (also created on server start). Placeholder WhatsApp number `0120000000` and generated PNG photos.

## Gotchas

- Scripts run with `tsx` and do not load `.env` by themselves: the package scripts pass `--env-file-if-exists=.env`. `--env-file` does not override variables already in the shell, so `DATABASE_URL=... pnpm seed` wins.
- Use top-level `await` in scripts and call `process.exit` (see `scripts/seed.ts`); keep scripts under `scripts/` and import the app with relative paths.
- After changing the schema: edit **both** schema files, run `pnpm db:generate`, `pnpm check:schemas`, and `pnpm check:backend` on SQLite and Postgres. Postgres never auto-syncs.
- The first account created is forced to admin, and `ensureOwner` only acts while there are no users; blank `SEED_ADMIN_*` on the command line when pointing scripts at a scratch database.
- better-sqlite3 needs its native build: `pnpm-workspace.yaml` lists it under `allowBuilds`. `next.config.ts` marks it, `pg` and `sharp` as `serverExternalPackages`.
- Turbopack traces the whole project for runtime `path.resolve(process.cwd(), ...)`; those calls carry `/* turbopackIgnore: true */`.
- Server actions allow 11 MB bodies (`experimental.serverActions.bodySizeLimit`) so 10 MB uploads fit.
- Uploads must be raster images. Do not add SVG back.
- **Parsing input:** `Fields` is strict. `number` accepts plain decimals only (blank is null, not 0; no hex, exponents, arrays or booleans; max 1e9), `id`/`ids` whole numbers up to 2147483647, `flag` real booleans or the words "true"/"false", `date` real calendar dates, and `text` strips control characters (a NUL breaks PostgreSQL). Every id that comes from a client goes through `assertId` in the actions. Page and limit numbers are clamped (`?page=1e20` used to be a 500).
- On SQLite `lower()` is replaced with a Unicode-aware function (`client.ts`), so `lower(col) like ...` folds accents the same way on both databases. PostgreSQL folds according to the database locale: a `C`-locale database cannot, an `en_US.UTF-8` one (the compose image) can.
- **Transactions:** `withTransaction(fn, { lock })` in `src/db/client.ts`. Use `lock: 'name'` for any rule that spans several rows (the last-admin rule uses `users:admins`): it takes a Postgres advisory lock so two transactions cannot both pass the check; SQLite already runs one transaction at a time. A nested call joins the outer transaction. On SQLite there is one connection, so another request's statement can run inside an open transaction: keep bodies short, no slow awaits.
- **Never log an error object from the data layer.** Drizzle's `Failed query` errors carry the bound parameters (password hashes, emails, whole records). Use `logError` / `describeError` from `src/server/result.ts`; `toFailure` only shows details when `NODE_ENV === 'development'`.
- The Postgres pool has an `error` listener (an idle connection dropped by a restart used to crash the process) and a statement timeout (`DB_STATEMENT_TIMEOUT_MS`, default 15 s; `pnpm migrate` turns it off).
- `updateSettings` merges `customTheme` into what is stored (send only what changes; null clears one key) and checks text contrast on the effective theme (preset + brand colour + custom colours) whenever any of them is sent.
- The build-time database fallback in `src/lib/queries.ts` only covers a missing database (unreachable server, missing file or table); other errors fail the build, and the fallback logs a warning.
- Some hooks in this setup ask for a short statement of facts before the first write or edit of each file, and block edits to `eslint.config.mjs`; that is the environment, not the project.

## Conventions

- Public site CSS is plain CSS in `src/app/(frontend)/styles.css`, driven by the theme variables. Admin UI uses shadcn/ui and Tailwind utilities.
- Use **pnpm** only (`pnpm install`, `pnpm dev`, `pnpm exec <bin>`, `pnpm --filter <package> add`); do not run `npm install`.
- Run `pnpm typecheck` and `pnpm lint` before finishing a change.
