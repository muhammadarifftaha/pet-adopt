# Pet Adopt: notes for Claude Code

Open-source storefront for adoptable pets. Visitors browse a catalog and contact the owners on WhatsApp or social media. No visitor accounts. Only the owners sign in, add pets, and build pages with a drag-and-drop editor.

Stack (versions pinned on purpose): Next.js 16.3.3, Drizzle ORM (SQLite via `@libsql/client` 0.18: a local file or, optionally, Turso; PostgreSQL via pg), Better Auth 1.7, Puck (`@puckeditor/core` ^0.24), shadcn/ui on Tailwind v4, React 19.2, TypeScript 5.7. **No Payload**: it was removed; the backend is our own (`src/db`, `src/server`).

## Layout (pnpm workspace + Turborepo)

- `apps/web`: the Next.js app, backend included (`src/`, `scripts/`, `drizzle/`, `pet-adopt.config.ts`, `.env`). Paths in this file that start with `src/`, `scripts/` or `drizzle/` are inside `apps/web`. Its scripts run with `apps/web` as the working directory.
- `packages/ui` (`@pet-adopt/ui`): the shadcn components, `cn` and `globals.css`, shared by the app and plugins (see "shadcn/ui" below).
- `packages/plugin-sdk` (`@pet-adopt/plugin-sdk`): what plugins and `pet-adopt.config.ts` import (`definePlugin`, `defineConfig`, `Plugin`, `EmailSender`, `PluginUser`...). It imports nothing from the app; keep it that way, so an npm plugin depends on it alone.
- `plugins/*`: workspace plugins (`@pet-adopt/plugin-adoption-tips`, `-form-builder`), each depending only on the SDK. They ship TypeScript source (no build step), so Next compiles them: `transpilePackages` is worked out by `localSourcePackages()` in `next.config.ts` from every dependency installed with `workspace:`, `link:` or `file:` (and their own local dependencies). Adding a plugin is `pnpm --filter @pet-adopt/web add <name>@workspace:*` (never `pnpm add` at the root) plus an entry in `pet-adopt.config.ts`; no `next.config.ts` edit. npm plugins should ship compiled JS and are left out.
- The registry, icon checks and plugin runtime stay in the app (`apps/web/src/plugins/`).
- `data/` (git-ignored, repo root): the local SQLite file. Default `DATABASE_URL=file:../../data/pet-adopt.db` (`DEFAULT_SQLITE_URL` in `client.ts`), relative to `apps/web`. Uploads never go to disk (S3 only, see Uploads); an older `data/media` is only read by `storage:copy-local`. SQLite creates the folder on open, never during `next build` (a missing folder counts as "no database" for the build fallback).
- Root scripts go through turbo (`pnpm typecheck`, `lint`, `build`, `check:schemas`, `check:backend`, `dev`) or `pnpm --filter @pet-adopt/web` (`migrate`, `seed`, `db:generate`, `admin:reset-password`). `turbo.json` uses `envMode: loose` so `DATABASE_URL` and friends reach the tasks. `turbopack.root` in `next.config.ts` is the repo root (pnpm installs `next` there and the plugins live outside the app).
- Drizzle stays in the app on purpose (one consumer); make `packages/db` only when a second program needs the database.

## Architecture

- **Routes:** `src/app/(frontend)` public site (`/`, `/pets`, `/pets/[slug]`, `/[slug]`). `src/app/(editor)/edit/[id]` the Puck editor (signed-in only). `src/app/media/[...path]` serves uploads. `src/app/api/auth/[...all]` is Better Auth. `/health` is a liveness probe. `src/instrumentation.ts` creates the first owner on start.
- **Database (`src/db`):** `schema/sqlite.ts` and `schema/pg.ts` are twins (Drizzle's two dialects have different table types). `client.ts` picks the dialect from `DATABASE_URL`: `postgres://`, a SQLite `file:`, or a hosted libSQL server (`libsql://`, `https://`, `http://` for a local `turso dev`; token in `DATABASE_AUTH_TOKEN`). Both SQLite kinds use `@libsql/client` and the same schema, migrations and queries. It turns WAL on for local files, sets a 5 s busy timeout, refuses to run if `PRAGMA foreign_keys` is off (libSQL turns them on for every connection by default), and provides `withTransaction`. `Database.migratesOnOpen` is true only for a local file, which applies pending migrations (site's, then plugins') on first open; Postgres and Turso are shared by every server instance and are migrated by `pnpm migrate` or **`pnpm build`**: apps/web's build script runs `scripts/migrate-on-build.ts` before `next build` (it is in the app's own script, not a turbo task, so a host that builds `apps/web` directly still migrates; `turbo.json` sets `build` to `cache: false` because a cache hit would skip it). It migrates Postgres and hosted libSQL and fails the build on error; skips a local SQLite file (it migrates on open, and the build must not create the file), Vercel preview builds (`VERCEL_ENV` not `production`, unless `MIGRATE_ON_PREVIEW=1`: previews usually share the production database) and `SKIP_BUILD_MIGRATE=1` (builds that cannot reach the database). `scripts/migrate-all.ts` (`migrateAll()`) is the one implementation behind `pnpm migrate` and the build step; both log failures with `describeError`, never the error object. Turso is a hosted service, so it is an opt-in only: the local file stays the zero-setup default. Turso itself was not tested against a live account. Constraint errors from libSQL carry the kind in `extendedCode` (`SQLITE_CONSTRAINT_UNIQUE`), which `hasCode` in `result.ts` checks. `pnpm db:generate` writes `drizzle/sqlite` and `drizzle/pg`; `pnpm check:schemas` fails when the schemas drift.
- **One set of repositories:** `src/server/*.ts` is written once against the SQLite-typed objects and cast to Postgres at one boundary in `client.ts`. Keep columns portable: ids are integers, timestamps are `Date`, booleans are booleans, lists and settings are JSON columns, date-only values are `YYYY-MM-DD` text, select options are plain text validated in the app. Case- and accent-insensitive search uses **stored folded columns** (`pets.search_text`, `pets.location_search`, `media.search_text`, migration 0011) filled on save with `foldText` from the SDK (NFKD, marks stripped, lower-cased) and queried with `like` on a folded, wildcard-stripped term, so it behaves the same on every database and locale. Never use `lower()` or `ilike` for this: libSQL cannot replace SQLite's ASCII-only `lower()`. Rows written before 0011 are filled by `backfillSearchText()` (`src/server/search-text.ts`, run at server start and by `pnpm migrate`). Small lists (theme names, form names, pet choices) compare and sort in JavaScript with `foldText` instead. Run `pnpm check:backend` on both databases after data-layer changes.
- **Data layer (`src/server`):** `pets.ts`, `pages.ts`, `media.ts`, `settings.ts`, `users.ts` hold the rules that used to be Payload hooks. `result.ts` has `Fields` (collects one error per field, keys like `nav.0.href`), `ValidationError`, `UserError` and `run()`. `actions/*.ts` are the `'use server'` functions the UI calls: each starts with `requirePermission('<area>:view|edit')` (or `requireUser()` for the person's own account, in `actions/auth.ts`) and returns `ActionResult`. The public pages read through `src/lib/queries.ts`, which keeps the old names and adds the build-time fallback.
- **Auth (`src/server/auth.ts`):** Better Auth with the Drizzle adapter (`usePlural`), the admin plugin (roles are plain text; see Roles and permissions), email and password, no sign-up, 2 hour sessions, cookie prefix `pet-adopt`. Sign-in is throttled by `src/server/throttle.ts`, shared by `signInAction` and the HTTP route `/api/auth/sign-in/email`: each attempt is counted **before** the password is checked, in one atomic upsert on the `rate_limits` table in three limits: 30 per client address, 5 per email **per client** (the everyday lockout, so one machine cannot lock an owner out), and 100 per hour per email overall (caps guessing spread over many addresses). A lock does not extend while active (the timestamp freezes once the limit is hit), and emails are SHA-256 hashed in the keys so the table never holds attacker-sized strings. Parallel guesses cannot slip past, and rows are purged opportunistically. `changePasswordAction` and the HTTP route `/api/auth/change-password` share one per-user counter (`guardPasswordChange`, key `chpw:<userId>`); Better Auth's own address-keyed rules for `/sign-in/email` and `/change-password` are switched off in `auth.ts`. IPv6 clients are reduced to their /64 prefix (`ipv6Prefix64`; IPv4-mapped addresses count as the IPv4). Recovery for a locked-out owner is `pnpm admin:reset-password` (`scripts/reset-password.ts`, password from `NEW_PASSWORD`). Better Auth's own limiter is switched off for that path (it keys on one address and would share a single bucket across all owners when it cannot parse the proxy header) and server actions skip it anyway. The client address is the entry `TRUSTED_PROXY_HOPS` (default 1) from the end of `CLIENT_IP_HEADER` (default `x-forwarded-for`) and must be a valid IP; entries before it are client-controlled, so the site must run behind a proxy you control. With no usable address the per-client limit is skipped (no shared "unknown" bucket) and production logs a warning once. The route handler is an **allowlist**: only `/api/auth/sign-in/email`, `change-password`, `sign-out` and `get-session` are open; everything else Better Auth ships (update-user, admin/*, sessions, sign-up, password reset...) returns 404, so role changes go through `users.ts` (last admin cannot be demoted or deleted; the first account is always admin) and nothing a future upgrade adds is exposed by default. The server start (`instrumentation.ts`) throws in production for a weak `BETTER_AUTH_SECRET` or a missing `NEXT_PUBLIC_SERVER_URL`. Accounts are created with `$context.internalAdapter`.
- **Roles and permissions** (agreed with the owner; the table lives in `packages/plugin-sdk/src/index.ts`, shared by the app and plugins): roles `admin`, `editor`, `developer`, `audit` (`ROLES`, labels and descriptions in `ROLE_INFO`). Permissions are `<area>:view` / `<area>:edit` over `pets`, `pages`, `media`, `theme`, `settings`, `plugins`, `users`, `pluginContent`, `personalData`, plus `personalData:export` (CSV download) and the activity log's `activity:own` (everyone), `activity:view` and `activity:export` (admin and audit). Admin: everything. Editor: pets, pages, media, plugin content and personal data (with export). Developer: pets, pages, media, plugin content, theme, settings, plugins; **no users and no personal data**. Audit: views everything, changes nothing, **cannot export**. `can(role, permission)` decides; `asRole()` reads a stored role and turns anything unknown into `audit` (changes nothing). Server: `requirePermission(p)` in `src/server/session.ts` (its error says "view only" when the role can view); pages use `requirePermissionPage(p)` (`src/lib/admin/unwrap.ts`, redirects to the dashboard); the menu items carry a `permission` (`nav-items.ts`) and a `section`: the sidebar (`AdminNav`) shows Dashboard, then **Content** (Pets, Pages, Media), **Plugins** (plugin screens and All plugins) and **Settings** (Email, Theme, Users, Activity, Site settings), in that order (agreed with the owner), leaving out a section the role has nothing in; the page builder opens **read-only** for roles without `pages:edit` (`PageEditor` `readOnly`: Puck `permissions` all off, which makes every field read-only; the custom pickers take Puck's `readOnly`; no Save or Publish in the header; picker choices only need `pages:view`). Screens a role can view but not change render view-only (`src/components/admin/view-only.tsx`: `<ViewOnly value>` around the screen, `ViewOnlyFieldset` disables the fields of each tab panel (tabs stay usable), `ViewOnlyNotice` at the top, write buttons hidden, and the rich-text editor reads `useViewOnly()` to stop editing). Plugin levels: `all` = `pluginContent`, `admin` = `plugins` (admins and developers), `personalData` (admins and editors; audit views; developers never). The last-admin rule still counts only `admin`. `check:backend` asserts the whole table and **scans every exported server action for a `requirePermission` call** (allowlist: own account, sign-in, public form submit and the builder's public reads); a new action without one fails the check.
- **Activity log** (agreed with the owner; `src/server/activity.ts`, pure parts in `src/lib/activity.ts`, table `activity_log`, migration 0013, screen `/admin/activity`): who changed what, and when. Recorded: every change (create, edit, delete, publish, restore, role changes, uploads, theme switches, settings), sign-ins, sign-outs, password changes and resets, **failed sign-ins** (actor null; the account it was aimed at as subject; the typed email is never stored, people type passwords into it) and downloads of personal data (form responses CSV, the log's own CSV). Not recorded: reads, test emails, marking responses as read. An entry holds the actor's id, name and role **as they were** (no foreign keys, entries outlive accounts and items), `action` (`pet.update`, `auth.sign-in-failed`, `form-builder.form.update`), `area` (filter), a one-sentence `summary`, the subject's id and name, **which fields changed (names only, never values**, so the log holds no personal data; `changedFields(before, after)` compares top-level keys deeply), and the client address (`clientAddress`). Role changes name the roles (not personal data). Server actions write the entry **after** the change succeeded with `recordActivity`, which never throws (a failure is logged; the change stands); inside `withTransaction` it would join the transaction. `check:backend` fails when an action that needs an `:edit` or `:export` permission does not call a `record…(` function (allowlist: `sendTestEmailAction`, `markResponsesReadAction`). Who sees what: everyone their own entries plus failed sign-ins on their account; admin and audit everyone's, with Person filter, client addresses and **CSV download** (`exportActivityCsvAction`, newest 50,000 entries, formula-safe cells via the SDK's `csvCell`, the download is itself logged). Retention `ACTIVITY_LOG_DAYS` (default **365**), purged at server start and at most hourly while the log is read. Plugins write with `host().recordActivity({ action, summary, subject?, fields? })`: the action must start with a configured plugin's name, area is `plugins`, and nothing is written with nobody signed in. Filters live in the URL; dates are picked as local days and sent as instants (`from` inclusive, `to` exclusive). The dashboard shows a **Recent activity** card (`components/admin/activity/RecentActivity.tsx`, `listRecentActivityAction`, newest 8 in the same scope, hidden if it fails to load) linking to the full log.
- **Password reset** (`src/server/password-reset.ts`, actions in `actions/password-reset.ts`, page `/admin/reset-password`): one-time links `<NEXT_PUBLIC_SERVER_URL>/admin/reset-password?token=<32 random bytes, base64url>`, never built from the request's Host. Only `sha256(token)` is stored, in Better Auth's `verifications` table (identifier `pwreset:<hash>`, value = user id, no migration needed); valid 1 hour, one use (claimed by `DELETE ... RETURNING`, so parallel uses cannot both win), a new link cancels older ones, banned accounts get none. Using one writes the credential and deletes every session in one transaction, then lifts sign-in lockouts. Links come from an admin (`createResetLinkAction`) or by email (`requestPasswordResetAction`), which validates and throttles first (`guardResetRequest`: 10 per client per 15 min, 3 per email per hour, keys `pwreset:*`), then does the lookup and sending in `after()`, so the answer and its timing are the same for unknown addresses. The page sets `referrer: no-referrer`. Better Auth's own reset endpoints stay 404.
- **Email** is built in (agreed with the owner): a generic **SMTP** sender (`src/server/email.ts`, nodemailer, `serverExternalPackages`), set up on the **Email** page (`/admin/email`, its own sidebar item under Settings; tabs **Sending** and **Templates**, `EmailNav`; `components/admin/settings/EmailSettingsForm.tsx`; the old `/admin/settings/email` and `/admin/settings/templates` redirect there). Who: `settings:edit` (admins and developers) change it, audit views it. Stored in `email_settings` (one row, id 1, migration 0014): host, port, security (`starttls` default 587, `tls` 465, `none` for local test servers), user name, sender name and address, reply-to, and the password **only encrypted** (`src/server/secret-box.ts`: AES-256-GCM, key by HKDF from `BETTER_AUTH_SECRET`, `v1.<iv>.<tag>.<data>`; another secret or a changed byte opens to null, and the screen then asks for the password again). The password never reaches a browser: the view has `passwordSet`; an empty box keeps it, `clearPassword` removes it. **Environment variables override single fields** (`SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM` = name and address, `EMAIL_REPLY_TO`); those fields show read-only with the variable's name, saving ignores them, and a bad value is listed as a problem. `getEmailSender()` (async, in `email.ts`) returns a ready **email plugin** first (the `email: { send, status? }` hook stays, for HTTP-API providers where SMTP ports are blocked; `getEmailPlugin()` in the registry, at most one), else the SMTP sender when ready, else null (no email form then). Plugins get it via `host().emailSender()` (now a Promise). The Resend plugin was removed (Resend offers SMTP). Saving is logged (`settings.email`, field names only). "Send a test email" (`sendTestEmailAction`, `settings:edit`, 5 per 15 minutes per person, key `emailtest:<userId>`) is on the Email screen and on an email plugin's page. **Development:** the compose `mailpit` service (1.33.1) accepts any mail (and any login) on loopback port 1025 and shows it at http://localhost:8025; messages are kept on disk (volume `pet_adopt_mailpit`, `MP_DATABASE`) so restarts keep the inbox. CI starts it, and `check:backend` sends real emails through it and reads them back via its API (`MAILPIT_URL`, default http://127.0.0.1:8025). **The checks delete only their own messages** (by their unique subjects, `DELETE /api/v1/search`): never call `DELETE /api/v1/messages`, it empties the developer's inbox.
- **Email templates** (agreed with the owner; pure format and rules in `src/lib/email-template.ts`, library and sending in `src/server/email-templates.ts`, actions in `actions/email-templates.ts`, table `email_templates`, migrations 0015 and 0016): every email has a **purpose** that decides its `{{placeholders}}` (`PURPOSE_INFO`; `{{siteName}}` and `{{siteUrl}}` everywhere). **System emails** (`SYSTEM_PURPOSES`: `password-reset`, which **requires** `{{resetLink}}`, and `test`) are edited in place (`/edit/email/password-reset`, `/edit/email/test`; one row per purpose, created on the first save by `saveSystemEmail` under the lock `email-templates:system`) and **Restore default** (`restoreSystemEmail`) deletes that row. **Everything else is "Templates"**, not tied to forms (any plugin uses them): `team-notification` (to the team; may hold the **Details** block of label/value pairs) and `visitor-message` (to someone outside the team; **never the Details block**: anyone can type any address into a public form, so it must not repeat what was typed), both with `{{title}}`. People make as many as they like; a template is **used only where something picks it**. **Plugin defaults** (agreed): a plugin lists `emailTemplates: [{ key, name, purpose, data? }]` (`PluginEmailTemplate`; the registry checks them, `getPluginEmailTemplates()`), seeded at server start and before listing (`ensurePluginTemplates`, row `seed_key` = `<plugin>:<key>`, unique); they can be edited and renamed, **never deleted**, and **Restore default** (`restoreSeededTemplate`) brings back the plugin's layout (`edited` compares with it). Which template an email uses (`pickTemplate`): a system email's edited copy; otherwise the picked `templateId` (same purpose), else the plugin default named by `fallback`, else the built-in `DEFAULT_TEMPLATES`. The form builder ships `form-builder:notification` ("Form response") and `form-builder:confirmation` ("Form confirmation") in `plugins/form-builder/src/email-templates.ts`, passes them as `fallback`, and its editor pre-selects them, so **a form's emails always have a template** (no "built-in" choice there). The builder (`/edit/email/<id>`, a second Puck config in `src/puck/email-config.tsx`: Heading, Text, Button, Image from the media library, Two columns (slots, no nesting), Divider, Space, and Details for team notifications; root fields subject, preview text, footer, and **the email's logo** at the top: the logo from Site settings (or the site's name without one), shown or hidden, size small/medium/large = 32/48/64 px, alignment, a link to the site, and optionally the site's name beside or under it (`logoLayout`: horizontal, horizontal-reverse, vertical, vertical-reverse; a small table so classic Outlook keeps it). There is no Logo block (agreed: the options live on the email's own logo). Missing logo options keep the old look (`LOGO_DEFAULTS`: shown, medium, centred, no link, no name)) draws each block with `blockHtml`, the same email-safe HTML that is sent (tables and inline styles, 600 px, theme colours from `emailThemeFrom`, logo, a media query stacking columns), plus plain text from `blockText`. **WebP in email** (agreed): classic Outlook and some older clients cannot show WebP, so `emailImageSrc` links a WebP upload (logo or Image block) as `/media/email/<name>.png` (`src/app/media/email/[name]/route.ts`): a lossless PNG made with sharp on the first request (first frame of an animation), kept in storage as `<name>.email.png` (`emailImageFilename`, allowed by `SAFE_STORAGE_KEY`, not served by `/media/`), and deleted by `removeUpload`; other formats and the builder's canvas use the original. Images carry no `outline` (unsupported in many clients) and the hidden preview text has `mso-hide:all`. Mailpit's HTML check scores what an email uses, so its percentage differs per email; the items left are graceful (border-radius, @media, `<body>` styles, the preview-text hiding). **Classic Outlook** is handled: bulletproof buttons (cell with `bgcolor` and `mso-padding-alt`), an Outlook-only 600 px wrapper, `bgcolor` attributes, 96 DPI; rounded corners and stacking are lost there. Everything typed and every value is escaped; links must be https/http, a site path, `{{siteUrl}}` (+path) or `{{resetLink}}`. `validateTemplate` rebuilds layouts from allowed parts on save (errors as `template.N`). **Screen** (Email > Templates, `/admin/email/templates`, `components/admin/settings/EmailTemplates.tsx`): one table (cards on phones) with System emails first (badge, Last edited = date or **Never**, Edit, Restore default), then the templates in name order: name (plus a **Default** badge for plugin defaults), type, **Used by** (plugins report it with `emailTemplateUsage` → `EmailTemplateUse` by `templateId` or `seedKey`; `getEmailTemplateUsage()` in the registry; forms that picked nothing count under the default), **Created by** (the person; blank for system emails and plugin defaults), last edited, Edit/View, Rename, Copy, Delete (not for defaults) or Restore default (edited defaults). **New template** asks for a name and the type. `settings:edit` builds, audit views (builder read-only). The builder's **Send test** sends the unsaved layout with sample values (test-email limit). Changes are in the activity log. Plugins send with `host().sendTemplatedEmail({ purpose, templateId?, fallback?, to, values: { title }, details? })` (false when email is not set up; details dropped for `visitor-message`) and list choices with `host().emailTemplates(purpose)` (`{ id, name, seedKey }`). Form builder: `notifyTemplateId`, and an opt-in visitor confirmation (`confirmationFieldId` must be an Email question, checked on save; `confirmationTemplateId`), sent after the answer (`confirmToVisitor`), at most 3 an hour per address (hashed key) and 10 per visitor; past that only the email is skipped. react-email was discussed as an alternative renderer; for now the HTML is hand-written.
- **Uploads:** `uploads.ts` checks the file really is JPEG/PNG/WebP/GIF with sharp (no SVG; **AVIF and HEIC are refused** with a message asking for JPEG, PNG or WebP, because their metadata, extra images and thumbnails are items in the file's offset tables that cannot be cut out and sharp does not report them all; sharp reports both formats as `heif`), refuses more than 40 megapixels, 12000 px on a side or 100 frames, then removes the metadata **without re-encoding** (`strip-metadata.ts`): it walks the JPEG segments / PNG and WebP chunks / GIF blocks and copies the ones that show the picture byte for byte, dropping EXIF (GPS, device, embedded thumbnail), XMP, IPTC, comments and anything after the end marker, so pixels, colour profile and animation are untouched (the check script proves identical decoded pixels). Orientation survives as a 26-byte EXIF block holding only that tag, so phone photos stay upright. Every format uses an **allowlist**: PNG and WebP copy only listed chunks, GIF only the image data plus timing and loop blocks that are **rebuilt from their fixed fields** (so extra bytes cannot ride along), and JPEG copies only the picture markers (tables, frame header, scan), the Adobe tag and the ICC profile, rebuilds the JFIF header with no thumbnail (JFIF can embed the original image), drops application segments and comments, and **refuses the whole file** on any other marker. The stripper fails closed: after it runs, sharp must read back the same format, size and frame count, or the upload is refused and the original is never stored. It names the result `<random hex>.<ext>` (the name people choose is only a label: `media.name`, migration 0009, cleaned by `cleanMediaName` in `src/lib/media-name.ts`, set from the upload dialog's "File name" or the uploaded file's own name, searched with the alt text), writes a `.thumb.webp` preview, and on any failure removes what it wrote and logs a file it cannot remove. Any decode failure becomes a field error on `file`. `storage.ts` is **S3-compatible object storage only**, by the user's decision (no local-disk option, so the server keeps no files and can be replaced, scaled or run serverless; `UPLOAD_DIR` is gone). Production refuses to start without valid settings (`s3Settings()` in `instrumentation.ts`; every route answers 500, so health checks fail), development warns and keeps going, and `next build` does not need them. `check:backend` stops with one message when `S3_BUCKET` is unset. CI starts the compose `garage` and `mailpit` services (`docker compose up -d --wait garage mailpit`, the same definitions as development), then runs `storage:check` and `check:backend`. `s3Settings()` reads and checks `S3_BUCKET`, `S3_ENDPOINT` (scheme and host only; unset for AWS), `S3_REGION` (default `us-east-1`, which AWS uses and other providers accept or ignore), both keys (required in production), `S3_FORCE_PATH_STYLE` (default: path style whenever an endpoint is set, since every S3-compatible server supports it) and `S3_PREFIX` (a folder inside the bucket, so sites or environments can share one). The client sends checksums only when the S3 API requires them (`requestChecksumCalculation`/`responseChecksumValidation: 'WHEN_REQUIRED'`): newer AWS SDKs add CRC32 checksums to every request by default, which some S3-compatible services reject. **Keep the code and docs provider-neutral: never name a particular storage provider.** `Storage` is `put`/`get`/`exists`/`delete`/`describe` (no secrets). `pnpm storage:check` writes, reads, checks and deletes a random test file with a hint per failing step; `pnpm storage:copy-local [--from <folder>] [--dry-run]` copies the uploads of a site that kept them on disk (default `data/media`) into the bucket, reading the folder directly, skipping files already there and names the server never generates. Verified against four S3 implementations (Garage, RustFS, SeaweedFS, VersityGW): `storage:check`, `check:backend` with uploads in the bucket, `storage:copy-local`, and `/media` serving byte-identical files from a production build. The dev server is **Garage** 2.5.0 in `docker-compose.yml` (chosen over RustFS for size: 7.6 MB of RAM at idle against 238 MB). `garage server --single-node --default-bucket` lays out a one-node cluster and creates the key (`GARAGE_DEFAULT_ACCESS_KEY`, which must be `GK` plus 24 hex characters, secret 64 hex) and the bucket `pet-adopt-media` on start; the config is inline (compose `configs.content`), with `s3_region = "us-east-1"` to match the app's default. S3 API on loopback port 9000 (container 3900); no web console (`docker compose exec garage /garage bucket info pet-adopt-media`). The image has no shell, so the health check is `/garage status`. Data survives restarts and `down`/`up` (volume `pet_adopt_garage`); `down -v` wipes it. URLs are `/media/<file>`; `next.config.ts` allows that path for `next/image`. Deleting an image that a pet, page or the logo uses is refused.
- **Pages:** `pages` has `puck_draft` and `puck_published` JSON columns, so saving a draft never changes the live page, and publishing copies draft to published (in one `UPDATE ... SET puck_published = puck_draft` when no data is sent, so a draft saved at the same moment cannot be overwritten). No version history, but `saveDraft`/`publishPage` take an optional `baseVersion` (the page's `updatedAt` in ms, returned as `version` by every save): if the page changed since, the save is refused with a "changed somewhere else, reload" error. The editor (`PageEditor`) carries it. Versions are matched as a one-millisecond window (`atVersion`), not with `=`, because PostgreSQL fills new rows with microsecond timestamps; each new version is `max(now, base + 1)`. `isPuckData` requires every block to have an object `props` and caps a layout at 1 MB and depth 30; NULs are stripped before saving. The homepage is always **id 1** (`HOME_ID`): it is created there, and a homepage found under another id swaps ids with the page on id 1 (through a spare id; `page_versions.page_id` is `ON UPDATE CASCADE`, migration 0005, so histories follow), then the id counter is moved past the highest id (`setval` on Postgres, `sqlite_sequence` on SQLite). The homepage keeps its slug (a field error on `slug`) and cannot be archived or deleted (server and UI); it can be unpublished, and then `/` shows `DEFAULT_HOME_DATA`. `stripTransient` removes render-only props (PetGrid's `pets`); add any new resolved prop to `TRANSIENT_PROPS`. **Archive and versions:** `pages.archived_at` marks an archived page: off the site (`getPublishedPage` returns null), read-only (`saveDraft`, `publishPage`, `savePageDetails`, `restorePageVersion` refuse with "archived"), keeping its slug; `restorePage` brings it back as it was, and `deletePage` only deletes an archived page. Every draft save, publish and version restore writes a snapshot to `page_versions` (`number` per page, `kind` draft/published/restored, `created_by`) inside the same transaction, under the lock `pages:<id>`; a draft identical to the latest snapshot (compared with es-toolkit `isEqual`, because jsonb reorders keys) is skipped, and only the latest `KEEP_VERSIONS` (50) are kept. **Page settings are part of the draft** (agreed with the owner; migration 0012): on a **live** page, saving the settings form (title, address, search description, share image) stores them in `pages.details_draft` (`PageDetails`), visitors keep the live columns, "Unpublished changes" and Publish changes appear, and `publishPage` applies them with the layout (re-checking the address; old and new paths revalidated). On a page that is not live they are written straight away. An address is checked against other pages' live **and** pending addresses (`assertSlugFree`, also for new pages). Versions store the settings too (`page_versions.details`, compared with the layout in `sameVersion`), so a settings-only change opens a version and restoring brings its title/address/SEO back (a system page keeps its address; versions from before 0012 have none and restore the layout only). The settings form and page builder show the draft settings; "View the live page" uses the live address (`PageFormPage.liveSlug`). **Restoring never rewrites history** (agreed with the owner): the old layout comes back as a **new** version with `restored_from` set (on version 3, restoring version 2 makes version 4; an open draft with unpublished work is kept as its own version, see `saveOpenVersion({ newVersion })`). "Restore as draft" (`restorePageVersion`) only replaces the draft; "Restore and publish" (`restoreAndPublishPageVersion`) does both in one transaction under the page lock, for a quick rollback. The page settings sidebar has a Versions card under Publishing (`components/admin/pages/PageVersions.tsx`: Live and Current draft badges, View opens a dialog with a sandboxed preview of `/edit/<id>/preview?version=N`, Newer/Older to click through, restore buttons only with `pages:edit` and not while archived; the sandbox has no scripts on purpose, so the console logs blocked-script lines for the preview). Snapshots do not count as image uses, so an image deleted later shows as missing in an old version. Signed-in previews: `/edit/<id>/preview[?version=N]` (editor layout, so the site CSS applies), shown in the admin table in a sandboxed iframe, which is why the CSP has `frame-src 'self'`.

- **Plugin storage** (a plugin added to a site that already runs gets its own tables without touching `src/db/schema`): a plugin sets `storage: definePluginStorage({ tables: { sqlite, pg }, migrations })` (`@pet-adopt/plugin-sdk`) and opens its tables with `storage.open()`. The SDK holds no database: the app registers the opener with `provideStorage` when `src/plugins/storage.ts` loads (instrumentation and the registry import it), in a `globalThis` slot so separate bundles share it, and finds the owning plugin by the identity of the handle (`getPluginByStorage`). Plugins list `drizzle-orm` as a peer dependency and never import the app. **Host services:** the same way, `host()` from the SDK gives plugins `requirePermission`, `requireUser` (fails closed: `pluginContent:edit`, so audit cannot write through a plugin written before roles), `requireAdmin` (`plugins:edit`), `run` (wrap every plugin server action in it), `clientAddress`, `consumeAttempt` (keys stored as `plugin:<key>`, purged with the rest), `phone.validate`/`toE164`, `emailSender` and `logError`; the app registers them in `src/plugins/host.ts` (loaded by the registry and instrumentation). `UserError`, `ValidationError`, `ActionResult` and `FieldErrors` are defined in the SDK and re-exported by `src/server/result.ts`, so `toFailure` recognises errors thrown by plugins. Plugin packages are not linted (ESLint only covers `apps/web`). Plugins come from npm packages or a local folder; both work the same because migrations are SQL **inlined** in a generated `migrations.ts` (`pnpm plugin:generate <folder> <name>` from the repo root, folder relative to where it is typed (`INIT_CWD`), runs drizzle-kit on `<folder>/schema/{sqlite,pg}.ts` into `<folder>/drizzle/` and pairs the two by name; commit `drizzle/` for its snapshots). `storage-rules.ts` checks at config load: every table and index starts with `pluginTablePrefix(name)` (`plugin_form_builder_`), the two schemas are twins (`src/db/compare-tables.ts`, shared with `check:schemas`), ids like `0000_init` in order, and the SQL names no site table (so **no foreign keys into core tables**, by decision; a heuristic against accidents, not a sandbox). Name long constraints yourself: Postgres cuts identifiers at 63 characters. `src/db/plugin-migrations.ts` runs them, each in a transaction under lock `plugins:migrate`, recorded in the core table `plugin_migrations` (plugin, migration, sha256 checksum; migration 0010); an edited or out-of-order migration is refused. **When they run:** `pnpm migrate` (after the site's own; required on Postgres and Turso); a local SQLite file also on open, where a failing plugin is logged and left not ready instead of stopping the site. **Not migrated yet:** `instrumentation.ts` warns at start (`warnAboutPluginStorage`), the plugin's screens show `PluginNotReady` instead (admins see what to run, editors "ask an admin"), its dashboard cards are hidden, and `/admin/plugins` shows "Needs migrate". `storage.open()` goes through `getPluginDatabase` and throws `PluginNotReadyError` (a `UserError`) until ready (form builder: `openFormsDatabase()` in `plugins/form-builder/src/storage.ts`; field model and answer checks in `src/fields.ts` (including the `source` question type: a dropdown filled from site data when the form is shown, `pets` for now through `host().choices('pets')` = `listPetChoices()` in `src/server/pets.ts`, listed and not adopted; the pick is checked against the current list when sent, stored as the label with `ref: 'pets:<id>'`; add a list by extending `CHOICE_SOURCES` in the SDK, `FORM_SOURCES` in the plugin and `choices` in `src/plugins/host.ts`), rules in `src/server.ts`, server actions in `src/actions.ts`, exported as `@pet-adopt/plugin-form-builder/{fields,server,actions}`). In a single-table Drizzle select, columns are written unqualified, so never reference the outer table inside a correlated subquery: use a join with `GROUP BY` (see `listForms`). Status is cached (ready forever, not-ready rechecked every 5 s; `forgetPluginStorageStatus()` for tests). Removing a plugin from the config keeps its tables and data; there is no drop command yet.
- **Caching:** public pages use `revalidate = 60` plus on-demand `revalidatePath` from the data layer (`safeRevalidate` swallows errors outside a request, e.g. in the seed script). `generateStaticParams` returns `[]`, so pages render on first visit.
- **Build without a DB:** `safely()` in `src/lib/queries.ts` returns fallbacks only while `NEXT_PHASE` is the production build, and `client.ts` refuses to open a missing SQLite file then (throws `SQLITE_CANTOPEN` itself, because libSQL would create it), so `next build` never creates a database file or its folder. ## Behaviour worth knowing (carried over, still true)

- **Pet slug:** generated from the name when blank (numbered when taken, `pet-<time>` for names with no Latin letters), kept on partial updates, validated against `SLUG_PATTERN`. Not required in the form because it is filled on the server.
- **Species is free text, not an enum** (owners can add their own). `SPECIES` in `src/lib/options.ts` only holds the usual ones (curated labels, form suggestions). Values are stored normalised by `normalizeSpecies` ("Guinea  Pig" -> `guinea-pig`; blank keeps the current value, no letters or digits is a field error), and `conditions()` normalises the filter, so every caller matches. `getSpeciesOptions()` (visible pets only, or `includeUnlisted` for the admin) feeds the catalog dropdown: built-ins first, then custom ones. `labelFor` shows an unknown value humanised ("Guinea pig"). `status` is different: it is the `PetStatus` enum.
- **Age is worked out from the birth date** (`src/lib/age.ts`), so it keeps up with the calendar. `birthDate` (`YYYY-MM-DD`) is the one source of truth; `birth_date_estimated` marks one that came from "about 8 months" (`ageValue` + `ageUnit` in `savePet`, stored as today minus that, so it never drifts; saving the same date again keeps the flag; a blank date next to an age means use the age). `toPet` and `summaries` replace `ageDescription` and `ageGroup` with the live values ("About 8 months", `baby`) whenever a birth date exists, so every page that reads them updates with no change. Without a birth date the typed `ageDescription` and picked `ageGroup` are used. The catalog's age filter is a date range from one table of limits (`GROUP_LIMITS`: baby under 6 months, young under 2 years, adult under 8, then senior), shared by the label and the SQL, with the stored group for pets that have no birth date. Every age function takes `today` so tests can move time.
- **Admin pet list (`/admin/pets`) uses SWR, not server refreshes.** The filters are URL params parsed with nuqs (`search-params.ts`); `FilterBar` writes them (search debounced 300 ms, default `shallow`, so the server is not asked), `PetList` and `FilterBar`'s pager (`PetPagination`, shadcn's `pagination`, real `<a>` links built with nuqs's `createSerializer`, page window from `src/lib/pagination.ts`) both call `usePetList` (`src/lib/admin/use-pet-list.ts`), which reads the committed URL with `useSearchParams()` and fetches `listPetsAction` through SWR (one request for both; key `["pets", search, status, species, page]`; no `keepPreviousData`, so a filter combination that is not cached yet shows `PetListSkeleton`, 12 placeholder cards with deterministic, varied text widths). The server page only seeds the first render (`fallbackData`, for that key only). SWR's cache is an in-memory `Map` in `(admin)/providers.tsx`, keyed by user id, never persisted; The species dropdown in `FilterBar` is SWR too (key `["pets", "species"]`, seeded by the page's `speciesOptions` prop), so one `useInvalidatePets()` refreshes lists and species together; it (`src/lib/admin/pets-cache.ts`) must be called after anything that changes pets from the client, because `revalidatePath` does not reach the browser cache. Fetchers use `unwrapResult` (`unwrap-client.ts`) so `{ ok: false }` becomes a thrown error SWR can see.
- **Health notes are rich text** stored as a Tiptap/ProseMirror JSON document in `pets.health_notes_doc` (the old plain `health_notes` column is legacy: never written now, and an old value is read as a document by `toPet`). `src/lib/rich-text.ts` is pure and the one authority: `validateRichText` **rebuilds** the document from allowed parts only (paragraphs, bullet and numbered lists, bold, italic, underline, links), so unknown nodes, marks and attributes cannot get through; links must be `/path` or `http(s)://` with no credentials (`isAllowedHref`); 2000 visible characters. `Fields.richText` uses it in `savePet`, and the zod schema reuses it. The editor (`RichTextField.tsx`) imports individual Tiptap extensions, not the StarterKit, and `check:backend` asserts that list matches the validator. Public pages render it with `RichText` (`src/components/site/RichText.tsx`), as React elements, never HTML. The health notes are not shown on the pet page yet.
- **City and state** are normalised (trimmed, whitespace collapsed). Saving either rebuilds `location` as "City, State" (once if equal, case-insensitively); a pet with neither keeps its own `location`. Catalog filters on city and state match exactly; `getLocationOptions()` returns the distinct values of listed pets.
- **Unlisted pets:** `unlisted` is link-only. Every listing query goes through `conditions()` in `src/server/pets.ts`, which hides them unless `includeUnlisted` is set (only the admin action sets it, and `queries.ts` strips it for public callers). `getPetBySlug` ignores the flag and the page sets `robots: noindex`. Any new public listing must apply the same filter.
- **Description** is rich text, exactly like the health notes but capped at 5000 visible characters (`DESCRIPTION_MAX_CHARS`): JSON in `pets.description_doc`, the old `description` text column is legacy (read as a document, cleared on the next save). `savePet` still accepts a plain string (one paragraph per line). The public pet page draws it with `src/components/site/RichText.tsx`, which renders the allowed nodes as React elements (never HTML) and re-checks each link.
- **Links and embeds:** use `safeHref` and `safeMapEmbed` from `src/lib/links.ts` for anything an owner can type into a block; social URLs and menu links are validated on save. WhatsApp numbers go through `normalizePhone` (`(0)` trunk prefixes are dropped).
- **Site settings form** (`/admin/settings`, `SettingsForm.tsx`, schema `src/lib/zod-schema/settings.ts` reusing `validatePhone`, `validateWebUrl`, `validateLink`): tabs Brand (name, tagline, logo, site icon, light/dark switch), Contact (WhatsApp, message, address, hours, social links) and Navigation (menu links, footer); lists use `useFieldArray` with up/down/remove buttons announced in a live region; `settingsFieldInfo` maps dotted error keys (`nav.1.href`) to their tab and label. Theme fields are not in this form. **WhatsApp number** uses `PhoneInput` (`src/components/admin/PhoneInput.tsx`: a Combobox of countries searchable by name, ISO code or `+60`, plus the number; a number pasted with `+code` switches the country on blur, a valid one is regrouped) over `src/lib/phone.ts`, which wraps `libphonenumber-js/max` (Google's metadata in a smaller library; the `/max` build validates like Google's, the default build only checks lengths) for the country list, `validatePhone` (too short / too long / `not valid for <country>`) and `toE164`. The form schema and `updateSettings` both use `validatePhone`, and the server stores **E.164** (`+60123456789`); numbers without a code are read as `NEXT_PUBLIC_DEFAULT_COUNTRY_CODE` (default 60, Malaysia). The pet form's `contactWhatsApp` still uses the older `normalizePhone` check. **Logo and site icon** are two separate images: `logo_id` (any shape; site header and the admin sidebar in `AdminShell`, which also puts the site name in admin tab titles) and `favicon_id` (migration 0008; the SQLite file had `ON DELETE SET NULL` added by hand again). `faviconProblem` in `settings.ts` requires a square (within 5%) of at least 32 px. `siteIcons(settings)` in `queries.ts` turns it into `icons` metadata, used by all four root layouts (frontend, admin, auth, editor); none set means no icon tag. `mediaUsage` counts both, so neither can be deleted while in use. `getSettings` in `queries.ts` is wrapped in React `cache`, so layouts and pages share one read per request.
- **Theme library** (`/admin/theme`, `theme:view`, changes need `theme:edit`; `src/server/themes.ts`, actions in `actions/themes.ts`, UI in `src/components/admin/theme/`): owners' saved themes in the `themes` table (`name`, `base` preset, `settings` = the customTheme shape), one active via `site_settings.active_theme_id` (`ON DELETE SET NULL`; the SQLite migration 0007 had that clause added by hand because drizzle-kit dropped it). `getSettings()` lays the active theme over `theme` / `customize` / `customTheme` (and clears `primaryColor`), so every reader of the theme follows it with no changes. Saving uses the settings' `parseCustomTheme` and `contrastProblem`; the theme in use cannot be deleted; `activateTheme({ preset })` returns to a built-in preset as designed. The editor's live preview is `/edit/theme-preview` (real blocks): the editor posts `themeCss(...)` to it with `postMessage` and `ThemePreviewBridge` applies it (same origin only, CSS as text).
- **Theming** (`src/lib/theme.ts`, Theme tab of site settings): pure TS. `PRESETS` give light and dark base colours plus fonts, radius, button style, shadow, density and text size; `resolveTheme` sanitises every input and `themeCss` emits `html:root{...}` plus dark-mode rules. `ThemeStyle` injects it with `dangerouslySetInnerHTML`, safe only because of that sanitising, plus a constant pre-paint script for the saved light/dark mode (`pet-adopt-mode` in localStorage, `data-mode` on `<html>`). Custom colours are checked for 4.5:1 contrast on save (`contrastProblem`), reported as `customTheme.light.text`. Derived `--muted` and `--primary-text` are nudged (`ensureContrastOnAll`) to 4.5:1 on every background they appear on (`--bg`, `--surface`, `--surface-alt`, `--tint`), not just the page. Focus rings use full-opacity `ring-ring` / `outline-ring` (`--primary-text`, so at least 3:1); do not reintroduce shadcn's `ring-ring/50` when adding components. Every colour, radius, shadow, font and spacing value in `styles.css` is a variable: keep it that way. The page builder layout uses `lightOnly`. Fonts are self-hosted `@fontsource-variable/*` imports in `fonts.ts`.
- **shadcn/ui is site-wide, in `packages/ui` (`@pet-adopt/ui`), laid out as shadcn's monorepo docs say:** components in `src/components` (`@pet-adopt/ui/components/button`), `cn` in `src/lib/utils.ts` (`@pet-adopt/ui/lib/utils`; the app's `@/lib/utils` re-exports it), hooks in `src/hooks`, and `src/styles/globals.css` (`@pet-adopt/ui/globals.css`; Tailwind, `tw-animate-css`, shadcn tokens), imported by the frontend, admin and auth layouts (the frontend one before `styles.css`). Inside the package, components import each other by the package's own name (its `tsconfig` paths). Both `apps/web/components.json` and `packages/ui/components.json` exist with matching style settings; run `pnpm dlx shadcn@latest add <name>` from `apps/web` and the CLI writes into `packages/ui`. Tailwind v4 only scans the app by default, so `globals.css` lists `@source` for `apps/web/src`, the package's components and `plugins/`: a class used anywhere else is left out of the CSS. Plugins build their admin screens with `@pet-adopt/ui` too. `@theme inline` there points shadcn's colour tokens at the site's own variables (`bg-primary` reads `--primary`, `text-muted-foreground` reads `--muted`, `bg-muted` reads `--surface-alt`), so components follow the theme and light/dark mode. The site's `--muted` is a text colour while shadcn's is a background: that is why they map differently. `styles.css` is unlayered, so it beats Tailwind's layered preflight and the public pages look as before. The editor layout does not load Tailwind. `packages/ui/src/components/` is generated by shadcn. The shadcn style is `base-nova` (components are built on **Base UI**, `@base-ui/react`, not Radix; `radix-ui` was removed). Base UI has no `asChild`: to render something else use the `render` prop (`<Dialog.Trigger render={<MyThing />} />`). For a **link that should look like a button**, do not use `<Button render={<Link />} nativeButton={false}>`, which gives the link button semantics (role, Space activates it); style a plain `<Link>` with `buttonVariants()` instead (see `src/components/auth/AuthNav.tsx`). New components are Base UI versions; `packages/ui/src/lib/utils.ts` re-exports `cn` from the `cn` package, which shadcn's own init installed. `FieldError` has `role="alert"`, so forms that can show several errors at once use plain error text plus one error summary instead (see the form builder's editor).
- **CSP** (`next.config.ts`): sent on every route. `default-src 'self'`; scripts and styles allow `'unsafe-inline'` (Next's inline bootstrap, and a nonce would end `revalidate` caching), plus `'unsafe-eval'` and `ws:` in development; `img-src 'self' data: blob:`; `frame-src https://www.google.com/maps/` (Contact block); `upgrade-insecure-requests` only when `NEXT_PUBLIC_SERVER_URL` is https. `CSP_REPORT_ONLY=1` switches to report-only. It is read at startup, so restart `next dev` after changing it. New external resources need a directive. The `/media` route's own stricter CSP is overridden by this global header.
- **Seed** (`scripts/seed.ts`): each step checks before it writes, so it is safe to re-run; it adds no pets if any non-sample pet exists, only fills settings while they are still the defaults, and refuses to run in production without `SEED_FORCE=1`. The owner comes from `SEED_ADMIN_*` (also created on server start). Placeholder WhatsApp number `0120000000` and generated PNG photos.

## Gotchas

- Scripts run with `tsx` and do not load `.env` by themselves: the package scripts pass `--env-file-if-exists=.env`. `--env-file` does not override variables already in the shell, so `DATABASE_URL=... pnpm seed` wins.
- Use top-level `await` in scripts and call `process.exit` (see `scripts/seed.ts`); keep scripts under `scripts/` and import the app with relative paths.
- After changing the schema: edit **both** schema files, run `pnpm db:generate`, `pnpm check:schemas`, and `pnpm check:backend` on SQLite and Postgres. Postgres never auto-syncs.
- The first account created is forced to admin, and `ensureOwner` only acts while there are no users; blank `SEED_ADMIN_*` on the command line when pointing scripts at a scratch database.
- libSQL ships prebuilt native binaries (no install script, nothing in `allowBuilds`). `next.config.ts` marks `@libsql/client`, `libsql`, `pg` and `sharp` as `serverExternalPackages`. The SDK and the form builder list `@libsql/client` as a dev dependency so pnpm resolves one `drizzle-orm` instance for the whole workspace; two instances make `SQL` types incompatible (run `pnpm dedupe` if `pnpm why @libsql/client` shows two versions). The SDK types plugin databases as Drizzle's driver-neutral `BaseSQLiteDatabase<'async', ...>` (`PluginDb`).
- Turbopack traces the whole project for runtime `path.resolve(process.cwd(), ...)`; those calls carry `/* turbopackIgnore: true */`.
- Server actions allow 11 MB bodies (`experimental.serverActions.bodySizeLimit`) so 10 MB uploads fit.
- Uploads must be raster images. Do not add SVG back.
- **Parsing input:** `Fields` is strict. `number` accepts plain decimals only (blank is null, not 0; no hex, exponents, arrays or booleans; max 1e9), `id`/`ids` whole numbers up to 2147483647, `flag` real booleans or the words "true"/"false", `date` real calendar dates, and `text` strips control characters (a NUL breaks PostgreSQL). Every id that comes from a client goes through `assertId` in the actions. Page and limit numbers are clamped (`?page=1e20` used to be a 500).
- **Transactions:** `withTransaction(fn, { lock })` in `src/db/client.ts`. Use `lock: 'name'` for any rule that spans several rows (the last-admin rule uses `users:admins`): it takes a Postgres advisory lock so two transactions cannot both pass the check; SQLite runs one transaction at a time per process. A nested call joins the outer transaction on both databases (the open transaction is kept in AsyncLocalStorage; on Postgres a nested `lock` is taken on that same transaction, which never waits on itself). Before this, a nested Postgres call ran on another pooled connection and committed on its own. `check:backend`'s "transactions" check covers nested rollback, locked read-modify-writes and the SQLite gate. **On SQLite** a transaction is a real libSQL transaction kept in AsyncLocalStorage, and `client.ts` wraps the libSQL client so every statement made in that async context (through `tx` or through the outer `db`) goes into it. On a local file, statements from other requests wait on an async gate until it commits (at most 5 s, then a `SQLITE_BUSY` error, like SQLite's own busy timeout; transactions waiting for each other have the same limit). The limit matters: code inside a transaction that awaits a promise another request started would otherwise wait forever. `migrate` inside a transaction is refused. That gate matters: libSQL's local driver is synchronous, and a statement busy-waiting for the write lock would block the event loop and deadlock the open transaction. Do not call Drizzle's `db.transaction()` on SQLite (the wrapper throws); use `withTransaction`. Keep bodies short, no slow awaits.
- **Better Auth errors:** inside the Next bundle the `APIError` Better Auth throws can be a different copy of the class than `better-auth/api` exports, so `instanceof` fails (only `tsx` scripts see one class). Use `isAuthError` in `actions/auth.ts` (class or `name === 'APIError'` with a `status`).
- **Never log an error object from the data layer.** Drizzle's `Failed query` errors carry the bound parameters (password hashes, emails, whole records). Use `logError` / `describeError` from `src/server/result.ts`; `toFailure` only shows details when `NODE_ENV === 'development'`.
- The Postgres pool has an `error` listener (an idle connection dropped by a restart used to crash the process) and a statement timeout (`DB_STATEMENT_TIMEOUT_MS`, default 15 s; `pnpm migrate` turns it off).
- `updateSettings` merges `customTheme` into what is stored (send only what changes; null clears one key) and checks text contrast on the effective theme (preset + brand colour + custom colours) whenever any of them is sent.
- The build-time database fallback in `src/lib/queries.ts` only covers a missing database (unreachable server, missing file or table); other errors fail the build, and the fallback logs a warning.
- Some hooks in this setup ask for a short statement of facts before the first write or edit of each file, and block edits to `eslint.config.mjs`; that is the environment, not the project.

## Conventions

- Public site CSS is plain CSS in `src/app/(frontend)/styles.css`, driven by the theme variables. Admin UI uses shadcn/ui and Tailwind utilities.

- Run `pnpm typecheck` and `pnpm lint` before finishing a change.
