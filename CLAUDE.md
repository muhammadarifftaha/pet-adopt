# Pet Adopt: notes for Claude Code

Open-source storefront for adoptable pets. Visitors browse a catalog and contact the owners on WhatsApp or social media. No visitor accounts. Only the owners sign in, add pets, and build pages with a drag-and-drop editor.

Stack (versions pinned on purpose): Next.js 16.3.3, Drizzle ORM (SQLite via `@libsql/client` 0.18: a local file or, optionally, Turso; PostgreSQL via pg), Better Auth 1.7, Puck (`@puckeditor/core` ^0.24), shadcn/ui on Tailwind v4, React 19.2, TypeScript 5.7. **No Payload**: it was removed; the backend is our own (`src/db`, `src/server`).

## Layout (pnpm workspace + Turborepo)

- `apps/web`: the Next.js app, backend included (`src/`, `scripts/`, `drizzle/`, `pet-adopt.config.ts`, `.env`). Paths in this file that start with `src/`, `scripts/` or `drizzle/` are inside `apps/web`. Its scripts run with `apps/web` as the working directory.
- `packages/ui` (`@pet-adopt/ui`): the shadcn components, `cn` and `globals.css`, shared by the app and plugins (see "shadcn/ui" below).
- `packages/plugin-sdk` (`@pet-adopt/plugin-sdk`): what plugins and `pet-adopt.config.ts` import (`definePlugin`, `defineConfig`, `Plugin`, `EmailSender`, `PluginUser`...). It imports nothing from the app; keep it that way, so an npm plugin depends on it alone.
- `plugins/*`: workspace plugins (`@pet-adopt/plugin-adoption-tips`, `-form-builder`), each depending only on the SDK. They ship TypeScript source (no build step), so Next compiles them: `transpilePackages` is worked out by `localSourcePackages()` in `next.config.ts` from every dependency installed with `workspace:`, `link:` or `file:` (and their own local dependencies). Adding a plugin is `pnpm --filter @pet-adopt/web add <name>@workspace:*` (never `pnpm add` at the root) plus an entry in `pet-adopt.config.ts`; no `next.config.ts` edit. npm plugins should ship compiled JS and are left out.
- The registry, icon checks and plugin runtime stay in the app (`apps/web/src/plugins/`).
- `data/` (git-ignored, repo root): the local SQLite file. Default `DATABASE_URL=file:../../data/pet-adopt.db` (`DEFAULT_SQLITE_URL` in `client.ts`), relative to `apps/web`. Uploads never go to disk (S3 only, see Uploads); an older `data/media` is only read by `storage:copy-local`. SQLite creates the folder on open, never during `next build` (a missing folder counts as "no database" for the build fallback).
- Root scripts go through turbo (`pnpm typecheck`, `lint`, `build`, `check:schemas`, `check:backend`, `dev`) or `pnpm --filter @pet-adopt/web` (`migrate`, `seed`, `db:generate`, `admin:reset-password`). `turbo.json` uses `envMode: loose` so `DATABASE_URL` and friends reach the tasks. `turbopack.root` in `next.config.ts` is the repo root (pnpm installs `next` there and the plugins live outside the app).
- Drizzle stays in the app on purpose (one consumer); make `packages/db` only when a second program needs the database.

## Architecture

- **Routes:** `src/app/(frontend)` public site (`/`, `/pets`, `/pets/[slug]`, `/[slug]`). `src/app/(editor)/edit/[id]` the Puck editor (signed-in only). `src/app/media/[...path]` serves uploads. `src/app/api/auth/[...all]` is Better Auth. `/health` is a liveness probe. `src/instrumentation.ts` creates the first owner on start (only with `SEED_ADMIN_*`) or prints the setup link. `src/app/(setup)/setup` is the first-time setup (its own root layout).
- **Database (`src/db`):** `schema/sqlite.ts` and `schema/pg.ts` are twins (Drizzle's two dialects have different table types). `client.ts` picks the dialect from `DATABASE_URL`: `postgres://`, a SQLite `file:`, or a hosted libSQL server (`libsql://`, `https://`, `http://` for a local `turso dev`; token in `DATABASE_AUTH_TOKEN`). Both SQLite kinds use `@libsql/client` and the same schema, migrations and queries. It turns WAL on for local files, sets a 5 s busy timeout, refuses to run if `PRAGMA foreign_keys` is off (libSQL turns them on for every connection by default), and provides `withTransaction`. `Database.migratesOnOpen` is true only for a local file, which applies pending migrations (site's, then plugins') on first open; Postgres and Turso are shared by every server instance and are migrated by `pnpm migrate` or **`pnpm build`**: apps/web's build script runs `scripts/migrate-on-build.ts` before `next build` (it is in the app's own script, not a turbo task, so a host that builds `apps/web` directly still migrates; `turbo.json` sets `build` to `cache: false` because a cache hit would skip it). It migrates Postgres and hosted libSQL and fails the build on error; skips a local SQLite file (it migrates on open, and the build must not create the file), Vercel preview builds (`VERCEL_ENV` not `production`, unless `MIGRATE_ON_PREVIEW=1`: previews usually share the production database) and `SKIP_BUILD_MIGRATE=1` (builds that cannot reach the database). `scripts/migrate-all.ts` (`migrateAll()`) is the one implementation behind `pnpm migrate` and the build step; both log failures with `describeError`, never the error object. Turso is a hosted service, so it is an opt-in only: the local file stays the zero-setup default. Turso itself was not tested against a live account. Constraint errors from libSQL carry the kind in `extendedCode` (`SQLITE_CONSTRAINT_UNIQUE`), which `hasCode` in `result.ts` checks. `pnpm db:generate` writes `drizzle/sqlite` and `drizzle/pg`; `pnpm check:schemas` fails when the schemas drift.
- **One set of repositories:** `src/server/*.ts` is written once against the SQLite-typed objects and cast to Postgres at one boundary in `client.ts`. Keep columns portable: ids are integers, timestamps are `Date`, booleans are booleans, lists and settings are JSON columns, date-only values are `YYYY-MM-DD` text, select options are plain text validated in the app. Case- and accent-insensitive search uses **stored folded columns** (`pets.search_text`, `pets.location_search`, `media.search_text`, migration 0011) filled on save with `foldText` from the SDK (NFKD, marks stripped, lower-cased) and queried with `like` on a folded, wildcard-stripped term, so it behaves the same on every database and locale. Never use `lower()` or `ilike` for this: libSQL cannot replace SQLite's ASCII-only `lower()`. Rows written before 0011 are filled by `backfillSearchText()` (`src/server/search-text.ts`, run at server start and by `pnpm migrate`). Small lists (theme names, form names, pet choices) compare and sort in JavaScript with `foldText` instead. Run `pnpm check:backend` on both databases after data-layer changes.
- **Data layer (`src/server`):** `pets.ts`, `pages.ts`, `media.ts`, `settings.ts`, `users.ts` hold the rules that used to be Payload hooks. `result.ts` has `Fields` (collects one error per field, keys like `nav.0.href`), `ValidationError`, `UserError` and `run()`. `actions/*.ts` are the `'use server'` functions the UI calls: each starts with `requirePermission('<area>:view|edit')` (or `requireUser()` for the person's own account, in `actions/auth.ts`) and returns `ActionResult`. The public pages read through `src/lib/queries.ts`, which keeps the old names and adds the build-time fallback.
- **Auth (`src/server/auth.ts`):** Better Auth with the Drizzle adapter (`usePlural`), **no admin plugin** (removed, agreed with the owner: we build our own; `role` and `archivedAt` are declared to Better Auth as `user.additionalFields` with `input: false`, permissions are our own table, see Roles and permissions; migration 0018 dropped the plugin's `banned`, `ban_reason`, `ban_expires` and `sessions.impersonated_by`), a `databaseHooks.session.create.before` that refuses archived accounts (error code `ACCOUNT_ARCHIVED`), the two-factor plugin (see Two-factor sign-in), email and password, no sign-up, 2 hour sessions, cookie prefix `pet-adopt`. Sign-in is throttled by `src/server/throttle.ts`, shared by `signInAction` and the HTTP route `/api/auth/sign-in/email`: each attempt is counted **before** the password is checked, in one atomic upsert on the `rate_limits` table in three limits: 30 per client address, 5 per email **per client** (the everyday lockout, so one machine cannot lock an owner out), and 100 per hour per email overall (caps guessing spread over many addresses). A lock does not extend while active (the timestamp freezes once the limit is hit), and emails are SHA-256 hashed in the keys so the table never holds attacker-sized strings. Parallel guesses cannot slip past, and rows are purged opportunistically. `changePasswordAction` and the HTTP route `/api/auth/change-password` share one per-user counter (`guardPasswordChange`, key `chpw:<userId>`); Better Auth's own address-keyed rules for `/sign-in/email` and `/change-password` are switched off in `auth.ts`. IPv6 clients are reduced to their /64 prefix (`ipv6Prefix64`; IPv4-mapped addresses count as the IPv4). Recovery for a locked-out owner is `pnpm admin:reset-password` (`scripts/reset-password.ts`, password from `NEW_PASSWORD`). Better Auth's own limiter is switched off for that path (it keys on one address and would share a single bucket across all owners when it cannot parse the proxy header) and server actions skip it anyway. The client address is the entry `TRUSTED_PROXY_HOPS` (default 1) from the end of `CLIENT_IP_HEADER` (default `x-forwarded-for`) and must be a valid IP; entries before it are client-controlled, so the site must run behind a proxy you control. With no usable address the per-client limit is skipped (no shared "unknown" bucket) and production logs a warning once. The route handler is an **allowlist**: only `/api/auth/sign-in/email`, `change-password`, `sign-out`, `get-session` and sign-in providers' callbacks (`/api/auth/callback/<slug>`) are open; everything else Better Auth ships (update-user, two-factor, sessions, sign-up, password reset...) returns 404, so role changes go through `users.ts` (last active admin cannot be demoted or archived; the first account is always admin) and nothing a future upgrade adds is exposed by default. The server start (`instrumentation.ts`) throws in production for a weak `BETTER_AUTH_SECRET` or a missing `NEXT_PUBLIC_SERVER_URL`. Accounts are created with `$context.internalAdapter`.
- **Roles and permissions** (agreed with the owner; the table lives in `packages/plugin-sdk/src/index.ts`, shared by the app and plugins): roles `admin`, `editor`, `developer`, `audit` (`ROLES`, labels and descriptions in `ROLE_INFO`). Permissions are `<area>:view` / `<area>:edit` over `pets`, `pages`, `media`, `theme`, `settings`, `plugins`, `users`, `pluginContent`, `personalData`, plus `personalData:export` (CSV download) and the activity log's `activity:own` (everyone), `activity:view` and `activity:export` (admin and audit). Admin: everything. Editor: pets, pages, media, plugin content and personal data (with export). Developer: pets, pages, media, plugin content, theme, settings, plugins; **no users and no personal data**. Audit: views everything, changes nothing, **cannot export**. `can(role, permission)` decides; `asRole()` reads a stored role and turns anything unknown into `audit` (changes nothing). Server: `requirePermission(p)` in `src/server/session.ts` (its error says "view only" when the role can view); pages use `requirePermissionPage(p)` (`src/lib/admin/unwrap.ts`, redirects to the dashboard); the menu items carry a `permission` (`nav-items.ts`) and a `section`: the sidebar (`AdminNav`) shows Dashboard, then **Content** (Pets, Pages, Media), **Plugins** (plugin screens; the list of every plugin is a **View all** link on the heading's line, a `SidebarGroupAction` for roles with `plugins:view`) and **Settings** (Email, Theme, Users, Authentication, Activity, Site settings), in that order (agreed with the owner; **Authentication**, `/admin/authentication`, `users:view`, has a side menu like Email: Two-factor, Sign-in providers and Archived accounts, `AuthenticationNav`), leaving out a section the role has nothing in; the page builder opens **read-only** for roles without `pages:edit` (`PageEditor` `readOnly`: Puck `permissions` all off, which makes every field read-only; the custom pickers take Puck's `readOnly`; no Save or Publish in the header; picker choices only need `pages:view`). Screens a role can view but not change render view-only (`src/components/admin/view-only.tsx`: `<ViewOnly value>` around the screen, `ViewOnlyFieldset` disables the fields of each tab panel (tabs stay usable), `ViewOnlyNotice` at the top, write buttons hidden, and the rich-text editor reads `useViewOnly()` to stop editing). Plugin levels: `all` = `pluginContent`, `admin` = `plugins` (admins and developers), `personalData` (admins and editors; audit views; developers never). The last-admin rule still counts only `admin`. `check:backend` asserts the whole table and **scans every exported server action for a `requirePermission` call** (allowlist: own account, sign-in, public form submit and the builder's public reads); a new action without one fails the check.
- **Activity log** (agreed with the owner; `src/server/activity.ts`, pure parts in `src/lib/activity.ts`, table `activity_log`, migration 0013, screen `/admin/activity`): who changed what, and when. Recorded: every change (create, edit, delete, publish, restore, role changes, uploads, theme switches, settings), sign-ins, sign-outs, password changes and resets, **failed sign-ins** (actor null; the account it was aimed at as subject; the typed email is never stored, people type passwords into it) and downloads of personal data (form responses CSV, the log's own CSV). Not recorded: reads, test emails, marking responses as read. An entry holds the actor's id, name and role **as they were** (no foreign keys, entries outlive accounts and items; a deleted account's entries are anonymised, see Deleting accounts), `action` (`pet.update`, `auth.sign-in-failed`, `form-builder.form.update`), `area` (filter), a one-sentence `summary`, the subject's id and name, **which fields changed (names only, never values**, so the log holds no personal data; `changedFields(before, after)` compares top-level keys deeply), and the client address (`clientAddress`). Role changes name the roles (not personal data). Server actions write the entry **after** the change succeeded with `recordActivity`, which never throws (a failure is logged; the change stands); inside `withTransaction` it would join the transaction. `check:backend` fails when an action that needs an `:edit` or `:export` permission does not call a `record…(` function (allowlist: `sendTestEmailAction`, `markResponsesReadAction`). Who sees what: everyone their own entries plus failed sign-ins on their account; admin and audit everyone's, with Person filter, client addresses and **CSV download** (`exportActivityCsvAction`, newest 50,000 entries, formula-safe cells via the SDK's `csvCell`, the download is itself logged). Retention `ACTIVITY_LOG_DAYS` (default **365**), purged at server start and at most hourly while the log is read. Plugins write with `host().recordActivity({ action, summary, subject?, fields? })`: the action must start with a configured plugin's name, area is `plugins`, and nothing is written with nobody signed in. Filters live in the URL; dates are picked as local days and sent as instants (`from` inclusive, `to` exclusive). The dashboard shows a **Recent activity** card (`components/admin/activity/RecentActivity.tsx`, `listRecentActivityAction`, newest 8 in the same scope, hidden if it fails to load) linking to the full log.
- **Sign-in providers** ("bring your own" OAuth 2 / OpenID Connect; agreed with the owner; rules and data in `src/server/auth-providers.ts`, actions in `actions/auth-providers.ts`, table `auth_providers` + `sessions.sign_in_method`, migration 0020; screen **Authentication > Sign-in providers**, `/admin/authentication/providers`, `AuthProviders`, `users:edit`, audit views): admins add **any number** of providers: an OIDC discovery URL, or the OAuth 2 authorization, token and user-info URLs by hand; client ID; client secret (**stored only encrypted** with secret-box, never sent back; blank keeps it, "Remove" clears it, none = public client with PKCE); scopes; on/off. Endpoints must be **https** (`validateEndpoint`: http only for a loopback host outside production; no credentials or fragment). The **slug** (Better Auth's provider id, in the redirect URI `<NEXT_PUBLIC_SERVER_URL>/api/auth/callback/<slug>`, shown with Copy) is made from the name once (`google`, `google-2`; `credential` and the like are reserved) and never changes. Better Auth's **`genericOAuth`** plugin is built from the enabled providers (`providerConfigs`) when `getAuth()` builds; saving calls `forgetAuth()` (rebuilt at once on that server) and other servers notice within 30 s (`providersVersion`: count and latest `updated_at`). **Linked first** (agreed): a provider never creates an account (`disableSignUp`, `disableImplicitSignUp`) and never links by a matching email (`accountLinking.disableImplicitLinking`); each person connects it while signed in on the **Account page** (`ConnectedProviders`, `connectProviderAction` → Better Auth `linkSocialAccount`; `allowDifferentEmails`, and the providers are `trustedProviders` because the person is signed in), after which **Sign in with <name>** on the sign-in page (`ProviderSignIn`, `startProviderSignInAction` → `signInSocial`, limited per client) signs them in. A provider account belongs to one account here. Disconnecting deletes that `accounts` row (`disconnectProvider`; passwords always stay); deleting a provider disconnects everyone. Provider tokens are stored encrypted (`encryptOAuthTokens`) and unused. **A provider sign-in counts as two-factor** (agreed): the session hook records `sign_in_method` (`password` or `provider:<slug>`; a session that replaces another, after a password change or turning two-factor on or off, keeps the method of the one it replaces), `SessionUser.signInMethod`, and `needsTwoFactorSetup` lets provider sessions through; archived accounts are refused by the same hook. Only the callback `/api/auth/callback/<slug>` opens on the HTTP route (pattern `PROVIDER_CALLBACK`); errors come back as `?error=<code>` to `/admin/login` (sign-in) or `/admin/account` (connecting), worded by `src/lib/auth-provider-errors.ts`. Provider sign-ins and connections happen in that route, so the Better Auth hooks log them (`recordProviderActivity`: `auth.sign-in` "Signed in with <name>", `account.provider-connect`); disconnecting and admin changes are logged by the actions. The sign-in and Account pages fall back to no providers if they cannot be read. `check:backend` runs the whole flow against a **mock OIDC provider** built into the script (Node `http` + `crypto`: discovery, JWKS, authorize, RS256 ID token with the nonce, userinfo).
- **Archived accounts** (agreed with the owner; `archiveUser`, `restoreUser`, `deleteUser` in `src/server/users.ts`, actions in `actions/users.ts`, column `users.archived_at`, migration 0019): the closest thing to a ban that keeps the person's name. Removing someone is **two steps, like pages: archive, then delete** (`deleteUser` refuses an active account). Archiving (`users:edit`, logged `user.archive`) signs them out everywhere and cancels pending reset links in one transaction under `users:admins`; **nobody archives themselves**, and the last **active** admin cannot be archived (archived admins do not count in `countAdmins`). An archived account cannot sign in: the session hook in `auth.ts` refuses every new session (password or two-factor code; the HTTP route answers 403), the right password gets "This account is archived. Ask an admin to restore it." and is logged (`auth.sign-in-archived`, `recordArchivedSignIn`), a wrong one looks like any wrong password, and `getSessionUser` ignores an archived user. It is read-only (no edits, new password or reset link), its email cannot be reused (createUser says to restore it), its name stays on page versions and email templates, and **Restore** brings it back as it was (role, password, two-factor). Deleting an archived account sets those `created_by` to null and **anonymises its activity log entries** (see Deleting accounts). Accounts are archived from the Users screen (whose count links to the archived list); **Authentication > Archived accounts** (`/admin/authentication/archived`, `ArchivedAccounts`, `users:view`, audit read-only) lists them with Restore and Delete.
- **First-time setup** (agreed with the owner; `src/server/setup.ts`, actions in `actions/setup.ts`, page `src/app/(setup)/setup/page.tsx` with its own root layout, steps in `src/components/setup/`, migration 0022): no seeded admin by default. **Claiming a new site:** while no account exists, the server prints a **setup link** to its log at start (`announceSetupLink`, a boxed message): `<NEXT_PUBLIC_SERVER_URL>/setup?key=<32 random bytes>`; opening `/setup` without a working key prints it again. The key is made once and stored **sealed** in `site_settings.setup_key_encrypted` (secret-box; written only into an empty slot, so every instance prints the same link), compared in constant time, and deleted when the first account exists. `createFirstAdmin` (key, then under the lock `setup:first-account` re-counts users, so two people at once cannot both succeed) makes an **admin** and signs them in. **Guided setup** (agreed: guided until finished or skipped, `site_settings.setup_done_at`): Your account, Your site (name, tagline, WhatsApp; `updateSettingsAction`), Theme (a built-in preset; `activateThemeAction`), Sample content (`src/server/sample-content.ts`: six example pets with pictures in the theme's colours and an About page; `removeSampleContent` takes them out), Email (the Email settings form; last on purpose, because working email switches the confirmed-email rule on), Done (image storage and email status, next steps). Every step can be skipped, and **Skip the rest of the setup** ends it (`finishSetupAction` only needs an admin role, not a confirmed email). The dashboard sends an admin to `/setup` until it is done; the sign-in page says "not set up yet" while no account exists. **Unattended installs** (agreed): `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` still create the first admin on start (`ensureOwner`), and the guided setup starts after signing in. Migration 0022 marks sites that already had accounts as set up, so an upgrade never sends them into it. `instrumentation.ts` skips the link during `next build` (it must not open the database).
- **Two-factor sign-in** (agreed with the owner; Better Auth's `twoFactor` plugin in `auth.ts`, rules in `src/server/two-factor.ts`, actions in `actions/two-factor.ts`, UI in `components/admin/two-factor/`, table `two_factors` + `users.two_factor_enabled` + `site_settings.two_factor_roles`, migration 0017): an **authenticator app (TOTP) plus ten one-time backup codes**; no email codes. Better Auth stores the secret and the codes **encrypted** with `BETTER_AUTH_SECRET`; our codes come from `generateBackupCodes` (`two-factor-codes.ts`: lower case without look-alikes, `xxxxx-xxxxx`; typed input is tidied by `normalizeBackupCode`/`normalizeTotpCode`), `two_factors.user_id` is unique. **Sign-in:** `signInAction` returns `SignInResult` (`{ twoFactor: true }` when a code is needed: no session yet, Better Auth's code-step cookie for 10 minutes); `verifyTwoFactorAction({ code, trustDevice })` takes the app code (6 digits) or a backup code in one box. A wrong code is a field error and is logged (`auth.two-factor-failed`, against the account named by our sealed `pet-adopt.2fa-pending` cookie, which only serves the log); 5 wrong per sign-in end it, **10 wrong in a row lock the code step for 15 minutes** (Better Auth's account lockout). **"Trust this browser"** skips the code for 30 days (`TRUST_DEVICE_DAYS`; records `trust-device-*` in `verifications`, all forgotten by `forgetTrustedDevices` on turning on, off and admin reset). **Setup** (Account page, `TwoFactorCard`): password, then the backup codes (shown once), then scan the QR (drawn on the server by `qrcode` as an SVG data URL, plus the key to type) and confirm a code, which turns it on; confirming is last on purpose (it replaces the session cookie and Next re-renders). New backup codes and turning off need the password (`guardPasswordChange` counter). **Required roles** (**Authentication** page, `/admin/authentication`, `TwoFactorRoles`, `users:edit`): someone in a ticked role without two-factor sees `TwoFactorRequired` instead of every admin screen (the `(admin)` layout; the editor layout and `requirePermissionPage` redirect to `/admin`) and **`requirePermission` refuses** (`needsTwoFactorSetup`); `requireUser` actions (own account) still work so they can set it up; they cannot turn it off. **Recovery:** an admin turns it off for someone else (`resetUserTwoFactorAction`, Users, logged; not for yourself), or `pnpm admin:reset-2fa <email>` (`scripts/reset-two-factor.ts`) for the last admin; **a password reset does not turn it off** (the mailbox would then be enough). Better Auth's `/two-factor/*` HTTP endpoints stay closed (route allowlist): an HTTP sign-in of an account with two-factor answers `twoFactorRedirect` and cannot be finished over HTTP. `check:backend` covers it with real TOTP codes.
- **Confirmed emails** (agreed with the owner; `needsEmailConfirmation`, `requestEmailVerification` in `src/server/email-change.ts`, `EmailConfirmBanner`): **every account must confirm its email before it can change anything**: `requirePermission` refuses every `:edit` and `:export` permission for someone whose `users.email_verified` is false (viewing and their own account actions still work). The rule applies **only while the site can send email** (otherwise nobody could confirm, and the owner could not set up email). Saving the email settings and sending a test email stay allowed for unconfirmed accounts (`requirePermission(p, { unconfirmed: true })` in `actions/email.ts`): otherwise a wrong SMTP setting would lock everyone out, because the confirmation email could not arrive. New accounts start unconfirmed (`createAccount`); accepting an invite, the confirmation link (system email **Confirm your email**, purpose `email-verify`, required `{{confirmLink}}`, the same `email-change:` link and `/admin/confirm-email` page carrying the current address, 24 hours, shared 5-an-hour limit) and confirming an email change confirm it; an admin's email change unconfirms it. Accounts from before the rule stayed confirmed (agreed). The `(admin)` layout shows the banner with **Send confirmation link**; Users shows "Email not confirmed". `requirePermission` loads the rule lazily (email-change reaches the plugin registry, whose host imports session.ts). ## Behaviour worth knowing (carried over, still true)

- **Pet slug:** generated from the name when blank (numbered when taken, `pet-<time>` for names with no Latin letters), kept on partial updates, validated against `SLUG_PATTERN`. Not required in the form because it is filled on the server.
- **Species is free text, not an enum** (owners can add their own). `SPECIES` in `src/lib/options.ts` only holds the usual ones (curated labels, form suggestions). Values are stored normalised by `normalizeSpecies` ("Guinea  Pig" -> `guinea-pig`; blank keeps the current value, no letters or digits is a field error), and `conditions()` normalises the filter, so every caller matches. `getSpeciesOptions()` (visible pets only, or `includeUnlisted` for the admin) feeds the catalog dropdown: built-ins first, then custom ones. `labelFor` shows an unknown value humanised ("Guinea pig"). `status` is different: it is the `PetStatus` enum.
- **Age is worked out from the birth date** (`src/lib/age.ts`), so it keeps up with the calendar. `birthDate` (`YYYY-MM-DD`) is the one source of truth; `birth_date_estimated` marks one that came from "about 8 months" (`ageValue` + `ageUnit` in `savePet`, stored as today minus that, so it never drifts; saving the same date again keeps the flag; a blank date next to an age means use the age). `toPet` and `summaries` replace `ageDescription` and `ageGroup` with the live values ("About 8 months", `baby`) whenever a birth date exists, so every page that reads them updates with no change. Without a birth date the typed `ageDescription` and picked `ageGroup` are used. The catalog's age filter is a date range from one table of limits (`GROUP_LIMITS`: baby under 6 months, young under 2 years, adult under 8, then senior), shared by the label and the SQL, with the stored group for pets that have no birth date. Every age function takes `today` so tests can move time.
- **Admin pet list (`/admin/pets`) uses SWR, not server refreshes.** The filters are URL params parsed with nuqs (`search-params.ts`); `FilterBar` writes them (search debounced 300 ms, default `shallow`, so the server is not asked), `PetList` and `FilterBar`'s pager (`PetPagination`, shadcn's `pagination`, real `<a>` links built with nuqs's `createSerializer`, page window from `src/lib/pagination.ts`) both call `usePetList` (`src/lib/admin/use-pet-list.ts`), which reads the committed URL with `useSearchParams()` and fetches `listPetsAction` through SWR (one request for both; key `["pets", search, status, species, page]`; no `keepPreviousData`, so a filter combination that is not cached yet shows `PetListSkeleton`, 12 placeholder cards with deterministic, varied text widths). The server page only seeds the first render (`fallbackData`, for that key only). SWR's cache is an in-memory `Map` in `(admin)/providers.tsx`, keyed by user id, never persisted; The species dropdown in `FilterBar` is SWR too (key `["pets", "species"]`, seeded by the page's `speciesOptions` prop), so one `useInvalidatePets()` refreshes lists and species together; it (`src/lib/admin/pets-cache.ts`) must be called after anything that changes pets from the client, because `revalidatePath` does not reach the browser cache. Fetchers use `unwrapResult` (`unwrap-client.ts`) so `{ ok: false }` becomes a thrown error SWR can see.
- **Health notes are rich text** stored as a Tiptap/ProseMirror JSON document in `pets.health_notes_doc` (the old plain `health_notes` column is legacy: never written now, and an old value is read as a document by `toPet`). `src/lib/rich-text.ts` is pure and the one authority: `validateRichText` **rebuilds** the document from allowed parts only (paragraphs, bullet and numbered lists, bold, italic, underline, links), so unknown nodes, marks and attributes cannot get through; links must be `/path` or `http(s)://` with no credentials (`isAllowedHref`); 2000 visible characters. `Fields.richText` uses it in `savePet`, and the zod schema reuses it. The editor (`RichTextField.tsx`) imports individual Tiptap extensions, not the StarterKit, and `check:backend` asserts that list matches the validator. Public pages render it with `RichText` (`src/components/site/RichText.tsx`), as React elements, never HTML. **Personality notes** (`pets.personality_notes_doc`, migration 0023) are the same kind of field (2000 characters, no legacy text column), on the Health and behaviour tab after Good with; the Pet page template's Pet health and Pet personality blocks show the two notes (Pet spotlight and Pet grid profiles show health notes only).
- **City and state** are normalised (trimmed, whitespace collapsed). Saving either rebuilds `location` as "City, State" (once if equal, case-insensitively); a pet with neither keeps its own `location`. Catalog filters on city and state match exactly; `getLocationOptions()` returns the distinct values of listed pets.
- **Unlisted pets:** `unlisted` is link-only. Every listing query goes through `conditions()` in `src/server/pets.ts`, which hides them unless `includeUnlisted` is set (only the admin action sets it, and `queries.ts` strips it for public callers). `getPetBySlug` ignores the flag and the page sets `robots: noindex`. Any new public listing must apply the same filter.
- **Description** is rich text, exactly like the health notes but capped at 5000 visible characters (`DESCRIPTION_MAX_CHARS`): JSON in `pets.description_doc`, the old `description` text column is legacy (read as a document, cleared on the next save). `savePet` still accepts a plain string (one paragraph per line). The public pet page draws it with `src/components/site/RichText.tsx`, which renders the allowed nodes as React elements (never HTML) and re-checks each link.
- **Links and embeds:** use `safeHref` and `safeMapEmbed` from `src/lib/links.ts` for anything an owner can type into a block; social URLs and menu links are validated on save. WhatsApp numbers go through `normalizePhone` (`(0)` trunk prefixes are dropped).
- **Site settings form** (`/admin/settings`, `SettingsForm.tsx`, schema `src/lib/zod-schema/settings.ts` reusing `validatePhone`, `validateWebUrl`, `validateLink`): tabs Brand (name, tagline, logo, site icon, light/dark switch), Contact (WhatsApp, message, address, hours, social links) and Navigation (menu links, footer); lists use `useFieldArray` with up/down/remove buttons announced in a live region; `settingsFieldInfo` maps dotted error keys (`nav.1.href`) to their tab and label. Theme fields are not in this form. **WhatsApp number** uses `PhoneInput` (`src/components/admin/PhoneInput.tsx`: a Combobox of countries searchable by name, ISO code or `+60`, plus the number; a number pasted with `+code` switches the country on blur, a valid one is regrouped) over `src/lib/phone.ts`, which wraps `libphonenumber-js/max` (Google's metadata in a smaller library; the `/max` build validates like Google's, the default build only checks lengths) for the country list, `validatePhone` (too short / too long / `not valid for <country>`) and `toE164`. The form schema and `updateSettings` both use `validatePhone`, and the server stores **E.164** (`+60123456789`); numbers without a code are read as `NEXT_PUBLIC_DEFAULT_COUNTRY_CODE` (default 60, Malaysia). The pet form's `contactWhatsApp` still uses the older `normalizePhone` check. **Logo and site icon** are two separate images: `logo_id` (any shape; site header and the admin sidebar in `AdminShell`, which also puts the site name in admin tab titles) and `favicon_id` (migration 0008; the SQLite file had `ON DELETE SET NULL` added by hand again). `faviconProblem` in `settings.ts` requires a square (within 5%) of at least 32 px. `siteIcons(settings)` in `queries.ts` turns it into `icons` metadata, used by all four root layouts (frontend, admin, auth, editor); none set means no icon tag. `mediaUsage` counts both, so neither can be deleted while in use. `getSettings` in `queries.ts` is wrapped in React `cache`, so layouts and pages share one read per request.
- **Theme library** (`/admin/theme`, `theme:view`, changes need `theme:edit`; `src/server/themes.ts`, actions in `actions/themes.ts`, UI in `src/components/admin/theme/`): owners' saved themes in the `themes` table (`name`, `base` preset, `settings` = the customTheme shape), one active via `site_settings.active_theme_id` (`ON DELETE SET NULL`; the SQLite migration 0007 had that clause added by hand because drizzle-kit dropped it). `getSettings()` lays the active theme over `theme` / `customize` / `customTheme` (and clears `primaryColor`), so every reader of the theme follows it with no changes. Saving uses the settings' `parseCustomTheme` and `contrastProblem`; the theme in use cannot be deleted; `activateTheme({ preset })` returns to a built-in preset as designed. The editor's live preview is `/edit/theme-preview` (real blocks): the editor posts `themeCss(...)` to it with `postMessage` and `ThemePreviewBridge` applies it (same origin only, CSS as text).
- **Theming** (`src/lib/theme.ts`, Theme tab of site settings): pure TS. `PRESETS` give light and dark base colours plus fonts, radius, button style, shadow, density and text size; `resolveTheme` sanitises every input and `themeCss` emits `html:root{...}` plus dark-mode rules. `ThemeStyle` injects it with `dangerouslySetInnerHTML`, safe only because of that sanitising, plus a constant pre-paint script for the saved light/dark mode (`pet-adopt-mode` in localStorage, `data-mode` on `<html>`). Custom colours are checked for 4.5:1 contrast on save (`contrastProblem`), reported as `customTheme.light.text`. Derived `--muted` and `--primary-text` are nudged (`ensureContrastOnAll`) to 4.5:1 on every background they appear on (`--bg`, `--surface`, `--surface-alt`, `--tint`), not just the page. Focus rings use full-opacity `ring-ring` / `outline-ring` (`--primary-text`, so at least 3:1); do not reintroduce shadcn's `ring-ring/50` when adding components. Every colour, radius, shadow, font and spacing value in `styles.css` is a variable: keep it that way. The page builder layout uses `lightOnly`. Fonts are self-hosted `@fontsource-variable/*` imports in `fonts.ts`.
- **shadcn/ui is site-wide, in `packages/ui` (`@pet-adopt/ui`), laid out as shadcn's monorepo docs say:** components in `src/components` (`@pet-adopt/ui/components/button`), `cn` in `src/lib/utils.ts` (`@pet-adopt/ui/lib/utils`; the app's `@/lib/utils` re-exports it), hooks in `src/hooks`, and `src/styles/globals.css` (`@pet-adopt/ui/globals.css`; Tailwind, `tw-animate-css`, shadcn tokens), imported by the frontend, admin and auth layouts (the frontend one before `styles.css`). Inside the package, components import each other by the package's own name (its `tsconfig` paths). Both `apps/web/components.json` and `packages/ui/components.json` exist with matching style settings; run `pnpm dlx shadcn@latest add <name>` from `apps/web` and the CLI writes into `packages/ui`. Tailwind v4 only scans the app by default, so `globals.css` lists `@source` for `apps/web/src`, the package's components and `plugins/`: a class used anywhere else is left out of the CSS. Plugins build their admin screens with `@pet-adopt/ui` too. `@theme inline` there points shadcn's colour tokens at the site's own variables (`bg-primary` reads `--primary`, `text-muted-foreground` reads `--muted`, `bg-muted` reads `--surface-alt`), so components follow the theme and light/dark mode. The site's `--muted` is a text colour while shadcn's is a background: that is why they map differently. `styles.css` is unlayered, so it beats Tailwind's layered preflight and the public pages look as before. The editor layout does not load Tailwind. `packages/ui/src/components/` is generated by shadcn. The shadcn style is `base-nova` (components are built on **Base UI**, `@base-ui/react`, not Radix; `radix-ui` was removed). Base UI has no `asChild`: to render something else use the `render` prop (`<Dialog.Trigger render={<MyThing />} />`). For a **link that should look like a button**, do not use `<Button render={<Link />} nativeButton={false}>`, which gives the link button semantics (role, Space activates it); style a plain `<Link>` with `buttonVariants()` instead (see `src/components/auth/AuthNav.tsx`). New components are Base UI versions; `packages/ui/src/lib/utils.ts` re-exports `cn` from the `cn` package, which shadcn's own init installed. `FieldError` has `role="alert"`, so forms that can show several errors at once use plain error text plus one error summary instead (see the form builder's editor).
- **CSP** (`next.config.ts`): sent on every route. `default-src 'self'`; scripts and styles allow `'unsafe-inline'` (Next's inline bootstrap, and a nonce would end `revalidate` caching), plus `'unsafe-eval'` and `ws:` in development; `img-src 'self' data: blob:`; `frame-src https://www.google.com/maps/` (Contact block); `upgrade-insecure-requests` only when `NEXT_PUBLIC_SERVER_URL` is https. `CSP_REPORT_ONLY=1` switches to report-only. It is read at startup, so restart `next dev` after changing it. New external resources need a directive. The `/media` route's own stricter CSP is overridden by this global header.
- **Seed** (`scripts/seed.ts`): each step checks before it writes, so it is safe to re-run; it adds no pets if any non-sample pet exists, only fills settings while they are still the defaults, and refuses to run in production without `SEED_FORCE=1`. The owner comes from `SEED_ADMIN_*` when set (also created on server start); the pets and the About page come from `src/server/sample-content.ts`, shared with the first-time setup. Placeholder WhatsApp number `0120000000`. **Six** sample pets (Mochi, Biscuit, Clover, Luna, Rocky pending, Whiskers adopted); 27 older ones are kept as `RETIRED_SAMPLES` so sites that have them can remove them and they never count as real pets. Their pictures are drawn from `apps/web/assets/sample-pet.png` (a cat silhouette, read at runtime, never served) in the active theme's primary colour on a soft shade of it, and each description ends with the image's credit as a link (Flaticon, "Kitty icons created by Boris farias"; the free licence asks for it).

## Gotchas

- **ESLint** covers every package: `apps/web/eslint.config.mjs` holds the rules (ignores `.next`, `node_modules` and `.remember`, a Claude Code plugin's scratch folder), and `packages/ui`, `plugins/form-builder` and `plugins/adoption-tips` each have an `eslint.config.mjs` that reuses it (with Next's `no-html-link-for-pages` off: they are not apps) and a `lint` script, so `pnpm lint` runs all four. The ecc plugin's config-protection hook blocks edits to ESLint configs; the owner turned it off for this project (`ECC_DISABLED_HOOKS=pre:config-protection` in `.claude/settings.local.json`).
- Scripts run with `tsx` and do not load `.env` by themselves: the package scripts pass `--env-file-if-exists=.env`. `--env-file` does not override variables already in the shell, so `DATABASE_URL=... pnpm seed` wins.
- Use top-level `await` in scripts and call `process.exit` (see `scripts/seed.ts`); keep scripts under `scripts/` and import the app with relative paths.
- After changing the schema: edit **both** schema files, run `pnpm db:generate`, `pnpm check:schemas`, and `pnpm check:backend` on SQLite and Postgres. Postgres never auto-syncs.
- The first account created is forced to admin, and `ensureOwner` only acts while there are no users; blank `SEED_ADMIN_*` on the command line when pointing scripts at a scratch database.
- libSQL ships prebuilt native binaries (no install script, nothing in `allowBuilds`). `next.config.ts` marks `@libsql/client`, `libsql`, `pg` and `sharp` as `serverExternalPackages`. The SDK and the form builder list `@libsql/client` as a dev dependency so pnpm resolves one `drizzle-orm` instance for the whole workspace; two instances make `SQL` types incompatible (run `pnpm dedupe` if `pnpm why @libsql/client` shows two versions). The SDK types plugin databases as Drizzle's driver-neutral `BaseSQLiteDatabase<'async', ...>` (`PluginDb`).
- Turbopack traces the whole project for runtime `path.resolve(process.cwd(), ...)`; those calls carry `/* turbopackIgnore: true */`.
- Server actions allow 11 MB bodies (`experimental.serverActions.bodySizeLimit`) so 10 MB uploads fit.
- Uploads must be raster images. Do not add SVG back.
- **Parsing input:** `Fields` is strict. `number` accepts plain decimals only (blank is null, not 0; no hex, exponents, arrays or booleans; max 1e9), `id`/`ids` whole numbers up to 2147483647, `flag` real booleans or the words "true"/"false", `date` real calendar dates, and `text` strips control characters (a NUL breaks PostgreSQL). Every id that comes from a client goes through `assertId` in the actions. Page and limit numbers are clamped (`?page=1e20` used to be a 500).
- **Transactions:** `withTransaction(fn, { lock })` in `src/db/client.ts`. Use `lock: 'name'` for any rule that spans several rows (the last-admin rule uses `users:admins`): it takes a Postgres advisory lock so two transactions cannot both pass the check; SQLite runs one transaction at a time per process. A nested call joins the outer transaction on both databases (the open transaction is kept in AsyncLocalStorage; on Postgres a nested `lock` is taken on that same transaction, which never waits on itself). Before this, a nested Postgres call ran on another pooled connection and committed on its own. `check:backend`'s "transactions" check covers nested rollback, locked read-modify-writes and the SQLite gate. **On SQLite** a transaction is a real libSQL transaction kept in AsyncLocalStorage, and `client.ts` wraps the libSQL client so every statement made in that async context (through `tx` or through the outer `db`) goes into it. On a local file, statements from other requests wait on an async gate until it commits (at most 5 s, then a `SQLITE_BUSY` error, like SQLite's own busy timeout; transactions waiting for each other have the same limit). The limit matters: code inside a transaction that awaits a promise another request started would otherwise wait forever. `migrate` inside a transaction is refused. That gate matters: libSQL's local driver is synchronous, and a statement busy-waiting for the write lock would block the event loop and deadlock the open transaction. Do not call Drizzle's `db.transaction()` on SQLite (the wrapper throws); use `withTransaction`. Keep bodies short, no slow awaits.
- **Better Auth errors:** inside the Next bundle the `APIError` Better Auth throws can be a different copy of the class than `better-auth/api` exports, so `instanceof` fails (only `tsx` scripts see one class). Use `isAuthError` in `actions/auth.ts` (class or `name === 'APIError'` with a `status`).
- **Never log an error object from the data layer.** Drizzle's `Failed query` errors carry the bound parameters (password hashes, emails, whole records). Use `logError` / `describeError` from `src/server/result.ts`; `toFailure` only shows details when `NODE_ENV === 'development'`.
- The Postgres pool has an `error` listener (an idle connection dropped by a restart used to crash the process) and a statement timeout (`DB_STATEMENT_TIMEOUT_MS`, default 15 s; `pnpm migrate` turns it off).
- `updateSettings` merges `customTheme` into what is stored (send only what changes; null clears one key) and checks text contrast on the effective theme (preset + brand colour + custom colours) whenever any of them is sent.
- The build-time database fallback in `src/lib/queries.ts` only covers a missing database (unreachable server, missing file or table); other errors fail the build, and the fallback logs a warning.
- Some hooks in this setup ask for a short statement of facts before the first write or edit of each file, and block edits to `eslint.config.mjs`; that is the environment, not the project.

## Conventions

- Public site CSS is plain CSS in `src/app/(frontend)/styles.css`, driven by the theme variables. Admin UI uses shadcn/ui and Tailwind utilities.
- Use **pnpm** only (`pnpm install`, `pnpm dev`, `pnpm exec <bin>`, `pnpm --filter <package> add`); do not run `npm install`.
- Run `pnpm typecheck` and `pnpm lint` before finishing a change.
